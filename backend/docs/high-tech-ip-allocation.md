# IP → RD 自动分配模块

## 使用方式

在高新申报的「项目详情表」点击「IP自动分配」。**无需预先填写研发活动名称或技术领域**；可先将知识产权汇总表的IP分配到RD，再点击「一键生成」，生成研发活动名称、科技成果名称及全表统一的PS名称。

名称生成按现有RD分组综合该RD的全部IP，不按IP数量新增RD。无IP的RD参考其他有IP的RD或已有RD名称生成相近方向的研发名称和成果，并记录参考来源。所有RD和成果生成后，再综合全表RD、IP及成果技术方向生成一个PS名称；所有项目行共用该名称，手工修改PS名称也会同步至全表。PS名称不依赖产品资料，不附加“待确认”标记。无IP且没有其他可参考RD名称时提示补充信息。生成过程保留编号、年份、周期与IP分配；校验或模型调用失败不覆盖原数据，成功后仍需保存草稿。

系统读取当前未保存的两张表，生成两轮分配预览。确认后仅填入项目详情现有的**IP序号、名称、授权号、授权日期、类型**五列，不新增列、不生成研发活动/成果/PS名称、不自动保存。用户仍须点击「保存草稿」持久化。取消、预览失败或输入发生变化时，不改变原有项目数据。

已有或部分填写的IP记录不会被覆盖。一个IP最多新增到一个RD；一个RD允许有多个IP。先复用该RD空白的IP分支，必要时新增分支，总行数不超过200。已有PS、成果、自定义字段保留；新分支的独立PS和成果信息需另外补充。没有合适IP的RD可以保留整组IP字段为空，但填写了一部分IP字段后，进入材料制作仍须补齐。

## 业务规则

本功能提供业务建议，不认定知识产权法律状态或申报资格。以下规则替代原有技术评分方案。

### 1. 时间硬约束

发明专利、实用新型、软件著作权共用规则：

- **申请日期 ≤ RD开始日期**：该IP—RD组合禁止自动分配，提示手动核对；等于开始日期也排除。
- **RD开始日期 < 申请日期 ≤ RD结束日期**：研发期内，优先；等于结束日期仍属于此档。
- **申请日期 > RD结束日期**：研发期后，作为后备。

时间校验针对每个组合执行：某个RD不能自动接收该IP，不影响该IP分配到其他时间合格的RD。名称相近不能绕过时间限制。

外观设计尚无自动规则，留给人工分配。编号缺失、研发周期无效或同一RD的分支周期冲突时，该RD不参与自动分配。**空RD名称、同一RD分支名称不同、默认技术领域均不影响分配**。缺失/无效的IP日期、授权信息以及重复的编号/授权号/名称均需人工核对。

### 2. 第一轮：先分散

- 已有IP的RD视为已覆盖，不再参加第一轮接收。
- 空RD在本轮最多接收一个IP；不因其有多个空白分支就分配多个IP。
- 全局求解依次优先：最大化可行分配数量（覆盖尽量多空RD）→最大化研发期内组合数量→优先项目表靠前RD。
- 不是按IP逐个贪心匹配；求解器可以重新调整此前选择，避免前面的选择阻碍后续IP分配。
- 研发期内优先于表格顺序，因此IP不足时不保证机械填入最前面的几个RD。
- 第一轮不调用AI，不提取五维语义、不使用技术分数，不依赖RD名称和技术领域。

### 3. 第二轮：只处理剩余IP

- 仅考虑时间合格、有行容量、且已有IP名称可作为比较依据的RD；依据包括历史IP和第一轮分配的IP。
- AI仅收到去重的IP名称及其临时ID，保守判断具体技术对象和核心用途是否相近。不能仅因共同包含「系统/平台/软件/智能」或属于同一行业就判定相近。没有明确依据时单独成组。
- **已有相近名称IP是追加条件**。没有时间合格且名称相近的对象时，剩余IP留给人工，不为了均衡而放入无关RD。
- 对满足追加条件的组合进行全局求解：最大化可行分配数量→研发期内优先→尽量均衡最终IP数量（计入历史和第一轮IP，最小化数量平方和）→优先项目表靠前RD。
- 不承诺数量完全相同；时间、名称相近条件及200行容量均可能使某些IP未分配或某些RD没有IP。

**不再使用原40/30/20/10权重、60分门槛、五维技术画像或临时RD主题。**

## 接口与运行限制

`POST /client/companies/:companyId/high-tech-application/ip-allocation/preview`

- 需要客户端登录、企业访问权限和高新申报项目权限。
- 请求体：`{ projects, ipSummary }`，两表各最多200行，行ID不得重复；该路由使用独立的10MB JSON上限。
- 返回结构：
  - `strategy: "spread_then_similar"`。
  - `assignments`：`ipId`、RD首行`projectId`、`rdNumber`、`timing: "within" | "after"`、`round: "spread" | "append"`、`reason`、`similarNames`。
  - `nameGroups`：第二轮名称分组，含`id`、原始`names`和`reason`；无需第二轮分析时为空。
  - `preserved`：已有分配的IP ID；`unassigned`：未分配IP及原因；`warnings`：手动核对提醒；`distribution`：各RD已有数量和本次新增数量。
- 不再返回`profiles`、`weights`、`threshold`及技术分数字段；前后端须同步更新。
- 第二轮复用现有AI网关和`AI_API_KEY`等配置，不新增数据库字段或优化器依赖。AI不接收RD名称、技术领域或日期，也不能决定RD归属、修改IP字段。
- **没有配置AI时仍可预览并确认第一轮结果**，剩余IP留给人工并显示提醒。没有剩余IP、没有可比较名称或已无接收容量时，不调用名称模型。
- 名称分析结果须完整覆盖输入ID且无重复/虚构ID，原因长度不超过240字。格式不正确、调用失败或超时则拒绝整个预览，不返回未验证的部分方案，不改变原有分配。
- 每个进程最多2个并发预览；每个预览第二轮至多1次名称分析，等待上限260秒；每轮最小费用流在独立Worker运行，上限15秒；前端请求超时300秒。
- 预览接口不读写持久化草稿。前端确认时检查企业与输入快照；输入变化后须重新生成预览。填入操作先构造完整替换结果，容量/重复等错误不会部分修改草稿。

## 验证

专项脚本：`backend/scripts/verify-high-tech-ip-allocation.cjs`。可用`HIGH_TECH_BUILD_DIR`指定隔离编译目录，避免改写生产构建。

覆盖：日期边界、三种IP类型、空RD名称、名称/领域无关性、已有/部分IP保护、重复身份、两轮容量限制、每轮100组随机穷举全局最优对照、40,000候选求解、第二轮名称证据/不相近留空、缺AI配置、无容量不调用AI、无效AI结果、预览并发限制、HTTP权限、大请求体及预览不落库。

用户提供的7IP、9个空名称RD（18分支）案例：7个IP分散到7个不同RD，3个组合处于研发期内；对应RD为RD01、RD02、RD03、RD04、RD06、RD07、RD08。RD05不机械优先于时间更合适的RD06/RD07/RD08。

前端API、纯填入逻辑和工作流测试覆盖：第一轮/第二轮展示、相近名称依据、手动提醒、现有五列、空RD名称下先分配再生成名称、快照失效、取消、显式确认、历史字段保留及容量失败时的原子性。

上述本地验证使用模拟AI/接口与隔离后端编译，不代表真实AI模型或真实企业数据已联调，也不代表已提交、推送或部署。
