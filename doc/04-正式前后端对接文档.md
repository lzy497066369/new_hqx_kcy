# 正式前后端对接文档

## 1. 目标

本文档描述后台管理系统 `vue-admin` 与正式后端 `backend` 之间的正式接口约定。当前仓库中的对应目录为 `vue-admin/apps/web-admin`，重点覆盖：

- 登录与退出
- 当前用户信息
- 菜单树
- 系统管理 CRUD
- 统一响应格式

## 2. 统一约定

后端统一返回：

```ts
{
  code: number;
  data: any;
  message: string;
}
```

- `code = 0` 表示成功
- `data` 承载业务数据
- `message` 承载错误或补充说明

请求认证方式：

- 登录后使用 `Authorization: Bearer <accessToken>`
- `refreshToken` 由后端通过 Cookie 维护

称呼统一：

- `vue-admin/apps/web-admin` = 后台管理系统，业务简称 `vue-admin`
- `vue-admin/apps/web-client` = 客户端操作系统，业务简称 `vue-client`
- `backend` = 正式后端

## 3. 核心接口

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/auth/login` | `POST` | 登录并返回 `accessToken` |
| `/auth/refresh` | `POST` | 刷新 `accessToken` |
| `/auth/logout` | `POST` | 退出登录 |
| `/auth/codes` | `GET` | 获取权限码列表 |
| `/user/info` | `GET` | 获取当前用户信息 |
| `/menu/all` | `GET` | 获取当前用户可见菜单树 |

## 4. 登录与用户信息

### 4.1 登录

`POST /auth/login`

请求体：

```ts
{
  username: string;
  password: string;
}
```

返回：

```ts
{
  accessToken: string;
}
```

### 4.2 当前用户信息

`GET /user/info`

返回示例：

```ts
{
  id: number;
  username: string;
  realName: string;
  roles: string[];
  permissions?: string[];
  homePath?: string;
  deptId?: number | null;
  deptName?: string | null;
}
```

### 4.3 菜单树

`GET /menu/all`

返回树形菜单数组，结构示例：

```ts
type MenuItem = {
  id: string;
  name: string;
  path: string;
  component?: string;
  redirect?: string;
  type: 'catalog' | 'menu' | 'button';
  status: number;
  authCode?: string;
  orderNum: number;
  meta: {
    title: string;
    icon?: string;
  };
  children?: MenuItem[];
};
```

## 6. 返回格式建议

### 6.1 列表接口

系统页列表建议返回：

```ts
{
  items: T[];
  total: number;
}
```

其中：

- 用户列表和角色列表适合分页返回
- 菜单列表和部门列表适合树形数组返回

### 6.2 树形接口

树形数据建议统一包含：

- `id`
- `parentId`
- `children`

## 7. 前端对接顺序

1. 启动 `backend` 和 `vue-admin/apps/web-admin`
2. 执行数据库初始化或升级脚本
3. 登录
4. 获取用户信息
5. 获取权限码
6. 获取菜单树
7. 再进入系统管理各页面

## 8. 后端开发重点

当前后端优先保证以下内容：

- 登录链路稳定
- 用户信息和菜单树稳定
- 系统管理模块可增删改查
- MySQL 5.6 兼容
- 接口返回格式统一
- 操作日志可写入并可查询
- 新环境初始化脚本和旧环境升级脚本都能执行

## 9. 数据库脚本执行方式

新环境执行：

- `backend/sql/schema.mysql56.sql`
- 如需要全国区域数据，再单独执行 `backend/sql/region-init-2025.sql`

已有环境升级：

1. 完整备份数据库。
2. 在 `backend` 下运行 `npm run db:migrate` 查看计划。
3. 运行 `npm run db:migrate:status` 只读核对已登记迁移和文件校验和。
4. 仅当旧库明确停留在 `2026-07-04` 基线时，运行 `npm run db:migrate -- --apply --allow-untracked-history`。
5. 若旧库历史执行状态不确定，先完成结构核对，再运行 `npm run db:migrate -- --adopt-current --confirm-adopt-current`，仅登记当前结构，不重跑历史 SQL。

说明：

- `sql/migrations/manifest.json` 是已有库的唯一受控升级顺序；不要再按文件名手工挑选补丁执行。
- 工具会将成功脚本登记到 `sys_schema_migration`，并保存 SHA-256；同一脚本内容被改动后会阻止继续发布。没有登记的旧库默认禁止直接重跑历史 SQL。
- 历史 `operation-log-*.sql`、`migrate_*.sql` 和 `fix-*.sql` 只用于定位特定旧库问题，不属于当前标准升级链路。
- `schema.sql` 仅保留作通用全量参考，线上新环境以 `schema.mysql56.sql` 为准。

## 10. 当前结论

后台管理系统已经进入正式联调和验收阶段。后端、前端和数据库脚本只要继续保持这套接口规范和字段命名一致，就可以稳定支撑后续系统管理页面与新业务模块的接入。
