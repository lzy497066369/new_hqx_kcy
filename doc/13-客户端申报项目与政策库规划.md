# 客户端申报项目与政策库规划

## 1. 规划目标

本阶段规划客户端的三块核心能力：

- 政策库：企业用户浏览区域政策文件，按地区、政策类型、项目、状态等条件检索，查看政策详情和附件。
- 申报项目项目列表：企业用户查看可申报项目，判断企业资料是否满足申报前置条件，并发起申报。
- 我的申报列表：企业用户查看当前企业已创建的申报，跟踪进度、材料缺口、审核状态和后续处理动作。

这三块功能必须依赖当前企业上下文和企业基本信息，不建议做成脱离企业资料的普通内容列表。

## 2. 当前基础

当前仓库已经具备以下基础：

- 客户端应用位于 `vue-admin/apps/web-client`，已有 `api/router/store/views` 分层。
- `src/store/client-enterprise.ts` 已提供当前企业、企业列表、企业资料、企业切换等上下文。
- `src/views/client/enterprise-profile` 已有基本信息、联系人、员工、财务、知识产权/科研项目、合同、证照、媒体资料等页面。
- `src/views/client/page-shell/index.vue` 已预留 `/policy/library`、`/projects/list`、`/projects/my` 的页面说明。
- `src/views/dashboard/workspace/index.vue` 已有“政策库”和“申报项目”快捷入口。
- 后端已存在政策管理基础模块：`policy/projects`、`policy/files`、`policy/regions`。
- `backend/sql/client-enterprise-menu-replan-patch.sql` 已规划客户端菜单：`/policy/library`、`/projects/list`、`/projects/my`。

参考项目 `technology_intelligence/vue-client/src/views/declare` 的结构可借鉴：

- `declare/index`：可申报项目入口、统计、筛选、创建申报、详情弹窗。
- `declare/list`：我的申报列表、状态统计、进度、截止时间、详情弹窗。
- `declare/project`：申报详情面板、时间节点、材料清单、待办、操作记录。

当前项目落地时不建议完整照搬视觉和字段，应吸收信息结构，并和企业资料完整度、政策库、当前企业上下文结合。

## 3. 信息架构

建议客户端菜单保持现在的目标路径：

| 一级 | 二级页面 | 路由 | 页面职责 |
| --- | --- | --- | --- |
| 政策中心 | 政策库 | `/policy/library` | 浏览政策文件、筛选、查看详情、下载附件 |
| 申报项目 | 项目列表 | `/projects/list` | 浏览可申报项目、匹配企业资料、发起申报 |
| 申报项目 | 我的申报列表 | `/projects/my` | 查看当前企业申报记录、状态、待补材料 |
| 申报项目 | 申报详情 | `/projects/my/:id` 或 `/projects/detail` | 查看申报进度、节点、材料、记录 |

如果动态菜单暂时只支持已有路径，申报详情可以先使用 query：`/projects/my/detail?id=xxx`。更推荐后续使用参数路由，便于面包屑和页面缓存。

## 4. 与基本信息的关联

申报和政策库不要直接复制一份企业信息。建议统一从 `useClientEnterpriseStore()` 和企业资料接口读取。

### 4.0 申报列表的政策召回规则

申报项目列表不应该直接展示全量项目，而应该先根据当前公司的所在区域召回相关政策，再从政策关联的统一项目生成“可申报项目列表”。

推荐召回链路：

```text
当前企业
  -> 企业基本信息 province/city/district
  -> 标准区域 biz_region 省/市/区节点
  -> 匹配本区 + 本市 + 本省政策文件
  -> 按 projectId 聚合为可申报项目
  -> 结合企业资料计算准备度
  -> 展示到 /projects/list
```

匹配优先级建议：

| 优先级 | 匹配范围 | 说明 |
| --- | --- | --- |
| 1 | 区/县政策 | 企业 `district` 命中的区县政策，最优先展示 |
| 2 | 市级政策 | 企业 `city` 命中的市级政策 |
| 3 | 省级政策 | 企业 `province` 命中的省级政策 |
| 4 | 通用政策 | 没有明确区域或适用全省/全国的政策 |

列表展示时建议保留来源说明，例如“来自合肥市政策”“来自安徽省政策”。同一个项目命中多条政策时，项目只展示一次，详情里列出命中的政策文件。

现有 `biz_enterprise_basic_info` 已有 `province`、`city`、`district` 文本字段，`biz_region` 已有 `parentId` 和 `level`。短期可以用文本匹配区域名称，长期建议给企业基本信息补标准区域外键：

| 字段 | 建议位置 | 用途 |
| --- | --- | --- |
| `provinceRegionId` | `biz_enterprise_basic_info` | 标准省级区域 ID |
| `cityRegionId` | `biz_enterprise_basic_info` | 标准市级区域 ID |
| `districtRegionId` | `biz_enterprise_basic_info` | 标准区县区域 ID |

这样后续政策匹配、统计、区域负责人分配都会更稳定。

### 4.1 政策库关联

政策库主要读取当前企业的这些资料，用于默认筛选和匹配提示：

| 基本信息来源 | 用途 |
| --- | --- |
| 企业注册地址/所属地区 | 默认匹配区域政策，优先展示本地政策 |
| 行业/企业类型 | 政策适用对象、行业方向匹配 |
| 统一社会信用代码、企业名称 | 政策详情页展示当前企业上下文 |
| 企业资料完整度 | 提示“完善资料后可获得更准确匹配” |

政策库页面可以先做普通列表，后续再加“匹配政策”。但页面上应保留匹配状态位，例如 `matchScore`、`matchReasons`、`missingFields`。

### 4.2 项目列表关联

项目列表必须显示当前企业是否具备申报基础：

| 基本信息来源 | 用途 |
| --- | --- |
| 基本资料完整度 | 发起申报前置校验 |
| 联系人 | 自动带入申报联系人 |
| 员工/研发人员 | 高企、科技型中小企业等项目评分或条件判断 |
| 财务/纳税/研发投入 | 项目匹配、预估评分、材料缺口 |
| 知识产权/科研项目 | 申报条件判断、材料引用 |
| 合同/证照/媒体资料 | 申报材料清单引用 |

项目卡片建议展示“可申报 / 需完善 / 不匹配 / 已申报”四类状态，而不是只有“立即申报”按钮。

### 4.3 我的申报关联

我的申报列表必须绑定当前企业：

- 切换企业后，列表重新加载当前企业的申报。
- 申报创建时记录 `companyId`、`projectId`、`policyFileId`。
- 申报详情页的材料清单优先引用企业资料库已有材料，缺失项进入待办。
- 企业基本信息变更后，可提示“资料有更新，是否刷新申报材料快照”。

建议申报保存时保留一份关键企业信息快照，避免后续企业资料变更导致历史申报内容失真。快照只用于申报详情展示和提交记录，不作为企业资料主数据。

## 5. 页面规划

### 5.1 政策库 `/policy/library`

页面目标：让企业用户快速找到政策文件，理解政策内容，并跳转到可申报项目。

推荐区块：

| 区块 | 内容 |
| --- | --- |
| 顶部概览 | 当前企业、匹配地区、政策总数、最新发布、即将截止 |
| 筛选区 | 关键词、地区、政策类型、统一项目、状态、发布时间 |
| 政策列表 | 标题、地区、项目、状态、负责人、更新时间、附件 |
| 政策详情抽屉/页面 | 政策正文、官方文件、附件、适用项目、责任人、更新时间 |
| 关联操作 | 查看项目、收藏、下载附件、联系项目老师 |

第一版建议复用现有后端 `GET /policy/files` 和 `GET /policy/files/:id`。客户端只展示 `published` 状态，后台管理端仍可查看草稿、归档、未完善。

### 5.2 项目列表 `/projects/list`

页面目标：展示可申报项目，帮助企业判断能不能申报、缺什么资料。

数据来源建议：

| 来源 | 用途 |
| --- | --- |
| 当前企业省/市/区 | 决定召回哪些区域政策 |
| `biz_region_policy_file` | 提供区域政策、政策详情、附件和项目关联 |
| `biz_policy_project` | 提供统一项目名称、类型、基础描述 |
| 项目申报条件/材料要求 | 计算企业准备度、材料缺口、是否可发起申报 |
| 当前企业资料库 | 判断基本信息、联系人、财务、知识产权等是否满足 |

推荐区块：

| 区块 | 内容 |
| --- | --- |
| 顶部统计 | 可申报项目数、资料待完善数、已申报数、热门项目 |
| 筛选区 | 关键词、政策类型、项目级别、地区、状态、是否推荐 |
| 项目卡片/列表 | 项目名称、政策类型、适用对象、简介、匹配状态、材料缺口 |
| 项目详情 | 项目介绍、申报条件、材料要求、关联政策文件、申报流程 |
| 发起申报 | 选择联系人、确认企业资料、生成材料清单、创建申报 |

发起申报前置建议：

- 无当前企业：引导去企业切换或绑定企业。
- 基本信息缺关键字段：阻止提交，跳转 `/company/profile` 或 `/company/basic`。
- 非关键资料缺失：允许创建草稿，但在申报详情中生成待办。
- 已存在进行中的同项目申报：提示进入“我的申报”继续处理。

### 5.3 我的申报列表 `/projects/my`

页面目标：让企业用户跟踪和继续处理申报。

推荐区块：

| 区块 | 内容 |
| --- | --- |
| 状态统计 | 全部、草稿、准备中、审核中、已通过、已驳回、已逾期 |
| 筛选区 | 状态、项目、关键词、截止日期 |
| 申报列表 | 项目名称、编号、当前节点、进度、截止日期、资料缺口、更新时间 |
| 操作 | 查看详情、继续完善、补充材料、撤回/取消、联系项目老师 |

列表状态建议：

| 状态 | 含义 |
| --- | --- |
| `draft` | 已创建，未提交 |
| `preparing` | 材料准备中 |
| `submitted` | 已提交审核 |
| `reviewing` | 项目老师/后台审核中 |
| `rejected` | 被退回，需要补正 |
| `approved` | 审核通过 |
| `completed` | 项目流程结束 |
| `cancelled` | 企业取消 |

### 5.4 申报详情

页面目标：承接参考项目 `declare/project` 的时间线和材料清单，但和当前企业资料库打通。

推荐区块：

| 区块 | 内容 |
| --- | --- |
| 申报总览 | 项目、当前状态、预估评分、剩余天数、材料完整度 |
| 节点时间线 | 阶段名称、开始/截止时间、节点说明、节点状态 |
| 材料清单 | 必需材料、辅助材料、已引用企业资料、待补材料 |
| 企业资料引用 | 基本信息、联系人、员工、财务、知识产权、合同、证照来源 |
| 待办事项 | 缺字段、缺文件、审核退回原因、即将逾期项 |
| 操作记录 | 创建、保存、提交、审核、退回、补正、完成 |

第一版可以先做详情页，不急着做复杂在线填报器。企业资料已在基本信息模块维护，申报详情负责“引用、提示缺口、提交”。

## 8. 数据模型建议

现有 `biz_policy_project` 和 `biz_region_policy_file` 可以支撑政策库基础展示，但不够支撑完整申报流程。

### 8.1 政策与项目字段扩展

建议把“政策文件”和“统一项目”职责分清：

- `biz_region_policy_file`：某个区域发布的一份具体政策文件，负责地区、标题、正文、附件、发布时间、截止时间、奖补金额等“政策原文维度”信息。
- `biz_policy_project`：跨区域复用的统一申报项目，负责项目名称、类型、适用对象、基础说明、通用条件等“项目模板维度”信息。

你提到的“前置条件”和“奖补金额”建议这样放：

| 信息 | 推荐位置 | 原因 |
| --- | --- | --- |
| 前置条件 | 优先放项目 requirement 表，政策文件可覆盖 | 条件通常和申报项目强相关，但不同区域政策可能有差异 |
| 奖补金额 | 优先放政策文件表 | 奖补金额通常跟具体地区政策相关，不同省市区可能不同 |
| 申报截止时间 | 政策文件表 | 截止时间来自具体政策通知 |
| 申报材料要求 | requirement 表，政策文件可覆盖 | 材料要求要参与准备度计算，结构化更好 |
| 适用对象 | 项目表 + 政策文件补充 | 项目有通用适用对象，政策可能有区域细则 |
| 申报级别 | 政策文件表或区域 level 推导 | 展示省级/市级/区县级 |

建议扩展 `biz_region_policy_file`：

| 字段 | 类型建议 | 用途 |
| --- | --- | --- |
| `start_date` | `date` nullable | 申报开始时间 |
| `end_date` | `date` nullable | 申报截止时间 |
| `subsidy_amount_min` | `decimal(12,2)` nullable | 最小奖补金额 |
| `subsidy_amount_max` | `decimal(12,2)` nullable | 最大奖补金额 |
| `subsidy_text` | `varchar(255)` nullable | 非固定金额描述，如“按投入比例补贴” |
| `application_level` | `varchar(32)` nullable | 国家/省/市/区县 |
| `condition_text` | `text` nullable | 政策原文里的申报条件补充 |
| `material_text` | `text` nullable | 政策原文里的材料要求补充 |
| `target_objects` | `varchar(255)` nullable | 适用对象补充 |

建议扩展 `biz_policy_project`：

| 字段 | 类型建议 | 用途 |
| --- | --- | --- |
| `project_level` | `varchar(32)` nullable | 通用项目级别 |
| `declare_period` | `varchar(128)` nullable | 常规申报周期描述 |
| `condition_summary` | `text` nullable | 通用前置条件摘要 |
| `material_summary` | `text` nullable | 通用材料摘要 |
| `sort_num` | 已有 | 项目展示排序 |

更推荐新增结构化 requirement 表，支撑准备度计算：

| 字段 | 类型建议 | 用途 |
| --- | --- | --- |
| `project_id` | `bigint` | 关联统一项目 |
| `policy_file_id` | `bigint` nullable | 为空表示项目通用要求，不为空表示某政策覆盖要求 |
| `requirement_type` | `varchar(32)` | `condition` 或 `material` |
| `source_module` | `varchar(32)` | 对应企业资料模块，如 `basic/finance/property` |
| `field_code` | `varchar(64)` nullable | 对应需要检查的企业资料字段 |
| `name` | `varchar(128)` | 条件或材料名称 |
| `description` | `text` nullable | 说明 |
| `required` | `tinyint` | 是否必需 |
| `sort_num` | `int` | 排序 |

有了 requirement 表，申报项目列表就可以展示：

- 是否满足前置条件。
- 缺哪些基本信息字段。
- 缺哪些材料。
- 是否允许先建草稿。
- 命中了哪些省市区政策。

建议后续新增或扩展：

| 表/模型 | 作用 |
| --- | --- |
| `biz_client_declaration` | 企业申报主表，记录企业、项目、状态、进度、快照 |
| `biz_client_declaration_material` | 申报材料清单，记录材料要求、企业资料引用、上传文件、状态 |
| `biz_client_declaration_node` | 申报节点，记录阶段、时间、状态 |
| `biz_client_declaration_log` | 操作记录，记录创建、提交、审核、退回、补正 |
| `biz_policy_project_requirement` | 项目申报条件和材料要求，供准备度计算 |

如果短期不想建太多表，第一阶段可以只建申报主表和材料表；节点和日志先用 JSON 字段或从状态生成，但后续建议独立建表。

## 9. 开发顺序

建议按小闭环推进：

1. 补前端路由和空页面：`/policy/library`、`/projects/list`、`/projects/my`。
2. 封装政策库 API：先接 `policy/files`、`policy/projects`、`policy/regions` 只读列表。
3. 实现政策库第一版：筛选、列表、详情抽屉、附件入口。
4. 封装项目列表 API：第一版可先复用 `policy/projects`，卡片展示项目基础信息。
5. 做项目列表第一版：项目卡片、详情抽屉、企业资料完整度提示。
6. 后端补申报主表和创建申报接口。
7. 前端实现发起申报弹窗：确认当前企业、联系人、资料缺口。
8. 实现我的申报列表：统计、筛选、列表、状态标签、继续处理入口。
9. 实现申报详情：总览、材料清单、时间线、待办、操作记录。
10. 打通企业资料引用：材料清单能跳转到基本信息、联系人、财务、知识产权等资料页补齐。

第一轮验收建议只要求：

- 当前企业上下文正确。
- 政策库能看列表和详情。
- 项目列表能看项目详情和企业准备度提示。
- 可以创建申报草稿。
- 我的申报能看到草稿并进入详情。

## 9.1 优先级规划

建议把客户端政策库和申报项目拆成 4 个阶段推进。核心原则是：先让企业按省市区看到相关政策和项目，再让企业能创建申报草稿，最后再做复杂的条件评分、材料自动引用和审核闭环。

### P0：区域政策召回与申报项目列表

目标：当前企业进入客户端后，能根据公司省市区看到相关政策和可申报项目。

| 顺序 | 任务 | 说明 |
| --- | --- | --- |
| 1 | 企业区域标准化 | 从企业基本信息拿 `province/city/district`，短期文本匹配，长期补 `provinceRegionId/cityRegionId/districtRegionId` |
| 2 | 政策召回规则 | 按区县、市、省、通用政策召回 `biz_region_policy_file` |
| 3 | 政策库列表 | `/policy/library` 展示已发布政策，支持地区、项目、关键词筛选 |
| 4 | 项目聚合列表 | `/projects/list` 按政策 `projectId` 聚合项目，同项目命中多条政策时只展示一次 |
| 5 | 项目详情抽屉 | 展示项目基础信息、命中政策、政策附件、适用地区 |

P0 暂不做完整申报流程，只解决“这个企业能看到哪些本地政策和项目”。

验收标准：

- 切换不同企业后，政策库和项目列表跟随企业地区变化。
- 区县企业能看到区县、市、省三级政策。
- 项目列表能显示“来源政策”和“适用地区”。
- 没有企业地区时，提示完善基本信息，不展示误导性全量列表。

### P1：政策字段补强与项目展示完整度

目标：让项目列表具备业务判断所需的基础字段，能展示奖补金额、截止时间、前置条件摘要。

| 顺序 | 任务 | 说明 |
| --- | --- | --- |
| 1 | 扩展政策文件字段 | 给 `biz_region_policy_file` 增加 `start_date/end_date/subsidy_amount_min/subsidy_amount_max/subsidy_text/application_level` |
| 2 | 扩展项目字段 | 给 `biz_policy_project` 增加 `declare_period/condition_summary/material_summary/project_level` 等展示字段 |
| 3 | 政策详情增强 | 政策详情展示奖补金额、申报时间、适用对象、附件 |
| 4 | 项目卡片增强 | 项目卡片展示奖补金额范围、截止时间、命中地区、政策数量 |
| 5 | 排序规则 | 优先展示区县政策、即将截止政策、资料更匹配项目 |

P1 重点是展示字段和排序，不强求自动判断企业是否完全符合。

验收标准：

- 项目列表能看到奖补金额、申报截止时间、政策级别。
- 政策详情能说明这个项目为什么出现在当前企业列表中。
- 同项目多政策时，能展示“最高奖补金额”或“多地区政策”提示。

### P2：前置条件与材料要求结构化

目标：把“前置条件”和“材料要求”结构化，开始计算企业申报准备度。

| 顺序 | 任务 | 说明 |
| --- | --- | --- |
| 1 | 新增 requirement 表 | 建议 `biz_policy_project_requirement`，支持项目通用要求和政策覆盖要求 |
| 2 | 条件配置 | 支持基本信息、联系人、员工、财务、知识产权、合同、证照等模块映射 |
| 3 | 准备度接口 | `/client/projects/:id/readiness` 返回可申报状态、缺失字段、缺失材料 |
| 4 | 项目列表状态 | 展示“可申报 / 需完善 / 不匹配 / 已申报” |
| 5 | 资料跳转 | 缺基本信息跳到基本信息页，缺材料跳到对应资料页 |

P2 开始把申报项目和基本信息真正打通，但仍可只做只读准备度，不急着做提交审核。

验收标准：

- 项目列表能说明缺哪些基本信息或材料。
- 发起申报前能判断关键字段是否缺失。
- 企业补齐资料后，准备度能刷新变化。

### P3：创建申报与我的申报列表

目标：企业能从项目列表创建申报草稿，并在“我的申报列表”持续跟踪。

| 顺序 | 任务 | 说明 |
| --- | --- | --- |
| 1 | 申报主表 | 新增 `biz_client_declaration`，记录企业、项目、政策、状态、快照 |
| 2 | 创建草稿 | `/client/projects/:id/declarations` 创建申报草稿 |
| 3 | 我的申报列表 | `/projects/my` 展示当前企业申报，支持状态筛选 |
| 4 | 申报详情骨架 | 展示申报总览、命中政策、材料清单、操作记录 |
| 5 | 材料清单 | 新增 `biz_client_declaration_material` 或先由 requirement 生成 |

P3 的第一版只需要“创建草稿 -> 我的申报能看到 -> 详情能进入”，不需要一次做完审核流。

验收标准：

- 同一个企业同一个项目避免重复创建进行中的申报。
- 切换企业后，我的申报列表不会串数据。
- 草稿详情能展示创建时的企业关键快照。

### P4：审核、补正与材料闭环

目标：把申报从草稿扩展到提交、审核、退回、补正和完成。

| 顺序 | 任务 | 说明 |
| --- | --- | --- |
| 1 | 提交申报 | `/client/declarations/:id/submit` |
| 2 | 审核状态 | 后台/项目老师审核，客户端展示审核中、已通过、已退回 |
| 3 | 补正材料 | 企业根据退回原因补材料或修改资料 |
| 4 | 操作记录 | `biz_client_declaration_log` 记录关键动作 |
| 5 | 通知待办 | 首页和我的申报展示待办、逾期、退回提醒 |

P4 是完整业务闭环，可以等 P0-P3 稳定后再做。

### 推荐先做的最小版本

如果现在马上开工，建议只做 P0 + P1 的前半段：

1. 公司地区标准化和政策召回。
2. `/policy/library` 政策库列表和详情。
3. `/projects/list` 按政策聚合的项目列表。
4. 给政策文件补 `end_date`、`subsidy_text`、`application_level` 这几个最影响展示的字段。
5. 项目详情里展示“命中的省市区政策”和“奖补/截止信息”。

这样先把用户最关心的“我公司所在地有哪些能申报的政策项目”跑通，再进入前置条件和我的申报。

## 10. 风险与取舍

- 现有政策接口是管理端语义，客户端直接使用时要注意只展示 `published` 数据，避免草稿和未完善政策暴露给企业用户。
- 现有政策项目字段不足，若要展示截止时间、扶持金额、申报条件、材料要求，需要扩展项目模型或新增 requirement 表。
- 申报流程不要在第一版就做复杂在线填报器，先把“企业资料引用 + 材料缺口 + 草稿提交”跑通。
- 企业资料变化会影响申报内容，需要区分企业主数据和申报快照。
- 切换企业后必须刷新政策匹配、项目准备度和我的申报列表，避免串企业数据。

## 11. 最小可落地版本

如果要尽快开始编码，建议第一版只做以下范围：

- `policy-library/index.vue`：政策列表、筛选、详情抽屉。
- `projects/list.vue`：项目列表、项目详情、发起申报按钮。
- `projects/my.vue`：我的申报列表、状态统计。
- `projects/detail.vue`：申报详情骨架、材料清单骨架。
- `api/client/policy.ts`、`api/client/declare-project.ts`、`api/client/declaration.ts`。
- 后端先补 `/client/declarations` 的列表、详情、创建草稿接口。

这样能先形成完整业务闭环，再逐步增强匹配评分、材料自动引用、审核流和收藏能力。
