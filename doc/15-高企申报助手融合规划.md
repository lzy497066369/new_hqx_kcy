# 高企申报助手融合规划

## 1. 规划结论

当前系统已经具备政策库、企业资料、申报项目、材料准备度、我的申报等基础能力。`declare-assistant` 中的高新技术企业申报功能不建议作为独立 Flask 应用直接接入，而应拆成可复用业务能力，融合进现有 NestJS + Vue Client 的申报链路。

推荐目标链路：

```text
政策库/申报项目
  -> 高企项目详情
  -> 企业资料准备度
  -> 高企评分测算
  -> 短板诊断和补齐建议
  -> 材料清单与申报草稿
  -> 高企申报书在线填报
  -> Word/PDF 导出与提交留档
```

第一阶段不要急着做完整在线申报书生成器。更优先的是把“高企能不能申报、差多少分、缺哪些材料、下一步补什么”做成一个稳定闭环。

## 2. 本轮落地口径

结合当前系统状态，本轮先按下面 5 条口径推进规划。后续开发时以这些边界为准。

| 序号 | 方向 | 落地口径 |
| --- | --- | --- |
| 1 | 评分引擎 | 重置当前评分模块，高企评分规则以 `declare-assistant` 的高企规则为蓝本，迁移为当前 NestJS 后端可维护的评分服务 |
| 2 | 诊断与准备度 | 在“我的申报详情”中增加评分诊断、风险等级、材料准备度、缺失项和补齐建议 |
| 3 | 申报书草稿 | 可以在申报书草稿中做测算和引用资料，但不可直接修改企业基本信息；需要修改时跳转到企业资料对应页面 |
| 4 | 申报书完善和导出准备 | 申报书完善、校验、导出准备阶段同样不可修改企业基本信息，只查看和引用企业资料 |
| 5 | 企业资料归口 | 公司信息、财务、人员、知识产权、证照、合同等资料统一在“企业资料”中补齐；“企业申报”只做查看、引用、测算、诊断、草稿和导出 |

核心边界：

```text
企业资料 = 主数据维护入口
企业申报 = 申报场景使用入口

企业申报中发现资料缺失
  -> 展示缺失原因和影响
  -> 提供“去补齐资料”跳转
  -> 不在申报页面直接改企业主数据
```

因此，后续页面设计要避免出现两套企业信息维护入口。申报模块只保存“本次申报快照”和“本次申报补充文本”，不反向覆盖企业资料主数据。

## 3. 现有系统基础

当前项目已经具备下列基础，适合作为高企申报助手的底座：

| 能力 | 当前状态 | 可承接高企能力 |
| --- | --- | --- |
| 客户端企业上下文 | 已有当前企业、企业切换、企业资料接口 | 高企评分和材料检查必须绑定当前企业 |
| 企业资料库 | 已有基本信息、财务、员工、知识产权、合同、证照、照片等模块 | 高企评分和申报书字段可从资料库读取 |
| 政策库 | 已有 `/client/policies`、政策列表和详情能力 | 高企项目可作为政策项目进入 |
| 申报项目 | 已有 `/client/projects`、项目详情、材料准备度接口 | 高企评分入口应挂在项目详情内 |
| 我的申报 | 已有申报草稿、申报列表、申报详情接口 | 高企申报书、评分结果、材料快照可绑定申报 |
| 材料准备度 | 已有 requirement/check 相关模型和接口 | 高企材料要求可结构化配置 |

## 4. declare-assistant 可复用能力

`declare-assistant` 中真正值得迁移的是业务逻辑和表单结构，而不是技术栈。

| 原功能 | 迁移建议 | 优先级 |
| --- | --- | --- |
| 高企评分规则 JSON | 改造成后端可配置评分规则或内置规则服务 | P0 |
| 高企评分计算 engine | 用 TypeScript 重写为 NestJS 服务 | P0 |
| 成长性指标计算 | 合并到评分服务，读取财务资料 | P0 |
| 规则型 AI 诊断 | 先迁移为非 AI 的短板诊断服务 | P0 |
| 财报字段提取 | 先不整体迁移，优先用现有企业财务资料 | P2 |
| 高企申请书大表单 | 拆成 Vue 页面/组件，挂在申报详情 | P2 |
| Word 导出 | 后端生成 docx，绑定申报记录留档 | P3 |
| PDF 导出 | 后续做，避免沿用 macOS Chrome 路径 | P4 |
| IP 证书 OCR | 暂不迁移，原项目已经停用 | 暂缓 |
| Flask 登录、Dashboard、SQLite 模型 | 不迁移 | 不做 |

## 5. 产品模块规划

### 5.1 高企项目入口

入口应放在客户端申报项目中，而不是新增一个孤立菜单。

建议路径：

| 页面 | 建议能力 |
| --- | --- |
| `/projects/list` | 高企项目卡片展示“可测算”“需完善资料”“已申报”状态 |
| `/projects/detail?id=高企项目ID` | 增加高企专项区块：评分测算、材料准备度、申报书入口 |
| `/projects/my-detail?id=申报ID` | 展示本次申报的评分结果、材料缺口、申报书草稿、导出文件 |

项目卡片建议增加高企特有摘要：

| 字段 | 说明 |
| --- | --- |
| `estimatedScore` | 预估评分 |
| `passLine` | 高企达标线，建议默认 71 |
| `scoreRiskLevel` | `low/medium/high` |
| `missingCoreItems` | 主要缺口，如知识产权、成果转化、研发费用 |
| `canStartAssessment` | 是否可以开始测算 |

### 5.2 高企评分测算

评分测算是第一期核心价值。

评分项建议按高企四大模块落库或内置：

| 模块 | 分值 | 数据来源 |
| --- | --- | --- |
| 知识产权 | 30 | 企业资料 `property/intellectualProperty`、人工补充分档 |
| 科技成果转化 | 30 | 研发项目、知识产权、产品、合同、成果转化记录 |
| 研发组织管理水平 | 20 | 制度文件、研发机构、产学研、激励制度、人才制度 |
| 企业成长性 | 20 | 财务资料，净资产增长率、销售收入增长率 |

第一版评分不必追求完全自动化。建议采用“系统自动取数 + 用户确认分档”的方式：

```text
企业资料自动取数
  -> 系统给出建议分档
  -> 用户/项目老师确认
  -> 保存评分快照
  -> 输出短板诊断
```

评分引擎重置建议：

| 层级 | 规划 |
| --- | --- |
| 规则层 | 以 `declare-assistant/modules/scoring/rules_gaoxin.json` 为蓝本，整理为当前系统的高企评分规则常量或数据库规则 |
| 计算层 | 用 TypeScript 重写评分计算，不直接复用 Python 代码 |
| 输入层 | 优先读取企业资料统计和专表数据，允许申报场景临时确认分档 |
| 快照层 | 每次测算保存输入快照、规则版本、分项结果和诊断结果 |
| 展示层 | 项目详情和我的申报详情都能查看最近一次测算结果 |

### 5.3 短板诊断

短板诊断先用规则引擎，不依赖 LLM。

建议输出：

| 输出 | 示例 |
| --- | --- |
| 综合判断 | 当前预估 68 分，距离达标线 71 分差 3 分 |
| 优势项 | 知识产权数量较完整，建议补强核心支持说明 |
| 短板项 | 成果转化数量不足、研发管理制度材料缺失 |
| 补齐建议 | 优先补 3 年成果转化证明、研发费用辅助账、研发制度文件 |
| 风险等级 | 高/中/低 |

LLM 只作为第二阶段增强，用于把结构化结果改写成申报口径文字。

### 5.4 高企材料准备度

复用现有材料准备度体系，为高企项目配置一套默认材料要求。

高企第一批材料要求建议：

| 模块 | 材料 |
| --- | --- |
| 基本信息 | 营业执照、企业简介、技术领域、联系方式 |
| 财务 | 近三年审计报告、研发费用专项审计、高新收入专项审计 |
| 员工 | 职工总数、科技人员名单、学历/职称结构 |
| 知识产权 | 专利/软著清单、证书附件、获得方式、关联产品 |
| 研发项目 | RD 项目立项、预算、费用归集、结题或阶段成果 |
| 成果转化 | 成果转化清单、合同、发票、验收或产品证明 |
| 制度文件 | 研发组织管理制度、成果转化激励制度、人才制度 |
| 产品服务 | PS 产品清单、收入、技术说明、关联知识产权 |

诊断与准备度在“我的申报详情”的展示建议：

| 区块 | 内容 |
| --- | --- |
| 高企评分概览 | 总分、达标线、是否达标、风险等级、最近测算时间 |
| 分项得分 | 知识产权、成果转化、研发管理、成长性分项得分和满分 |
| 短板诊断 | 主要失分项、影响说明、补强优先级 |
| 材料准备度 | 准备度分数、缺失材料数量、必交材料缺失提示 |
| 补齐建议 | 按企业资料模块聚合，例如“去补齐财务资料”“去维护知识产权” |
| 申报动作 | 重新测算、查看材料清单、继续申报书草稿 |

### 5.5 高企申报书

申报书建议在 P2 开始做，页面不要一次性塞完整大表单。应拆为分步式填报：

| 步骤 | 内容 |
| --- | --- |
| Step 1 | 企业基本信息和主要情况 |
| Step 2 | 知识产权汇总 |
| Step 3 | 人力资源情况 |
| Step 4 | 研发活动 RD |
| Step 5 | 研发费用结构 |
| Step 6 | 高新产品服务 PS |
| Step 7 | 成果转化和创新能力 |
| Step 8 | 标准参与、附件核对、导出 |

表单字段应优先引用企业资料库，允许用户在申报书里补充本次申报专用内容。正式提交或导出前生成申报快照，避免后续企业资料变化影响历史申报。

申报书草稿里的字段分两类：

| 类型 | 是否可在申报书中修改 | 处理方式 |
| --- | --- | --- |
| 企业主数据 | 不可修改 | 只读展示，提供跳转到企业资料对应模块 |
| 申报专用内容 | 可修改 | 保存到高企申报书草稿，例如 RD 描述、PS 技术说明、成果转化说明 |

企业主数据包括企业名称、统一社会信用代码、注册地址、联系人、财务记录、员工记录、知识产权、证照、合同、照片等。申报书页面只做引用和展示，不做主数据维护。

## 6. 技术架构建议

### 6.1 后端模块

建议新增或扩展后端模块：

```text
backend/src/modules/client
  继续承接客户端高企接口

backend/src/modules/declaration/gaoxin
  gaoxin-rule.service.ts
  gaoxin-score.service.ts
  gaoxin-diagnosis.service.ts
  gaoxin-book.service.ts
```

如果暂时不拆新模块，也可以先放在 `client.service.ts` 周边，但评分规则、诊断和申报书生成逻辑不要长期堆在一个大 service 里。

### 6.2 建议接口

第一期接口：

```http
GET  /client/projects/:id/gaoxin-assessment
POST /client/projects/:id/gaoxin-assessment
POST /client/projects/:id/gaoxin-assessment/recalculate
GET  /client/declarations/:id/gaoxin-assessment
```

第二期接口：

```http
GET  /client/declarations/:id/gaoxin-book
PUT  /client/declarations/:id/gaoxin-book
POST /client/declarations/:id/gaoxin-book/generate-word
GET  /client/declarations/:id/gaoxin-book/download
```

### 6.3 建议数据表

第一期最少新增：

| 表 | 用途 |
| --- | --- |
| `biz_gaoxin_score_record` | 保存评分结果、分项得分、诊断结果、评分快照 |
| `biz_gaoxin_score_rule` | 可选，保存评分规则版本；短期也可内置 JSON |

第二期新增：

| 表 | 用途 |
| --- | --- |
| `biz_gaoxin_book_draft` | 保存高企申报书草稿 JSON |
| `biz_gaoxin_book_export` | 保存导出文件路径、版本、导出时间 |

评分记录建议字段：

| 字段 | 说明 |
| --- | --- |
| `enterprise_id` | 企业 ID |
| `declaration_id` | 可为空；绑定具体申报时填写 |
| `project_id` | 高企项目 ID |
| `total_score` | 总分 |
| `pass_score` | 达标线 |
| `passed` | 是否达标 |
| `breakdown_json` | 分项得分 |
| `diagnosis_json` | 诊断建议 |
| `input_snapshot_json` | 评分输入快照 |
| `rule_version` | 规则版本 |

## 7. 开发阶段

### P0：重置评分引擎

目标：按 `declare-assistant` 高企规则重置评分模块，让企业能在高企项目详情里完成一次测算，看到分数、短板和补齐建议。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 从 `declare-assistant` 迁移高企评分规则为 TypeScript 常量或 JSON |
| 2 | 实现高企评分服务：知识产权、成果转化、研发管理、成长性 |
| 3 | 从企业资料读取基础数据，缺失项允许前端手动补充分档 |
| 4 | 保存 `biz_gaoxin_score_record` |
| 5 | 项目详情页增加“高企评分测算”区块 |
| 6 | 输出短板诊断和补齐建议 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 可测算 | 高企项目详情能生成评分 |
| 可解释 | 每个分项有得分、满分、依据 |
| 可追溯 | 评分输入和规则版本可保存 |
| 可行动 | 能看到优先补齐建议 |

### P1：诊断与准备度进入我的申报详情

目标：把高企评分短板和材料缺口结合起来，并在“我的申报详情”中展示。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 配置高企默认材料要求 |
| 2 | 将评分短板映射到材料要求 |
| 3 | 项目详情展示“评分风险 + 材料准备度” |
| 4 | 创建申报草稿时保存最近一次评分结果 |
| 5 | 我的申报详情展示缺失材料和评分风险 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 材料可查 | 能列出高企缺哪些材料 |
| 资料可跳转 | 缺财务/知识产权/员工资料可跳到对应资料页 |
| 申报有关联 | 创建申报后能看到本次评分结果 |

### P2：申报书草稿

目标：把申报书做成分步式草稿，而不是一次性大表单。申报书草稿可以测算、引用资料和补充申报专用文字，但不可修改企业基本信息。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 新增高企申报书草稿表 |
| 2 | 做分步填报页面 |
| 3 | 企业资料自动带入基础字段，字段只读展示 |
| 4 | 基本信息缺失时提供跳转到企业资料对应模块 |
| 5 | RD、PS、成果转化支持从企业资料中选择引用 |
| 6 | 保存草稿并显示完整度 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 可填写 | 八个步骤能保存和回显 |
| 可引用 | 能从企业资料选知识产权、研发项目、合同等 |
| 可校验 | 必填项缺失能提示 |
| 不串入口 | 企业基本信息只能跳转到企业资料修改，申报书不直接编辑 |

### P3：申报书完善和导出准备

目标：申报书完善、校验和导出准备全部基于企业资料引用和申报草稿，不直接修改企业基本信息。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 完善 Step 5-8：费用、PS、成果转化、创新能力、附件核对 |
| 2 | 对企业资料字段做只读校验，缺失则跳转补齐 |
| 3 | 确定 Word 模板来源，放入项目受控目录 |
| 4 | 设计导出数据结构和模板字段映射 |
| 5 | 后端生成 docx，不依赖用户桌面路径 |
| 6 | 导出文件写入 `biz_gaoxin_book_export` |
| 7 | 申报详情展示导出历史并支持重新生成 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 可导出 | 生成 Word 文件 |
| 可下载 | 申报详情能下载历史文件 |
| 可复现 | 模板和数据快照可追踪 |
| 不改主数据 | 导出前发现企业资料问题，只提示并跳转，不在导出页修改 |

### P4：AI 辅助撰写

目标：用 AI 辅助写 RD、PS、成果转化和创新能力文字。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 统一后端 LLM 配置和调用日志 |
| 2 | 为 RD/PS/创新能力设计结构化 prompt |
| 3 | 增加“一键生成/重新生成/采纳”交互 |
| 4 | 对 AI 内容加人工确认状态 |
| 5 | 记录生成来源和时间 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 可控 | AI 内容不自动提交，必须人工采纳 |
| 可追踪 | 生成记录可查 |
| 可降级 | 没有 LLM 时不影响评分和申报主流程 |

### P5：企业资料补齐闭环

目标：把公司信息统一沉淀到企业资料模块，企业申报只查看和引用。

任务：

| 顺序 | 任务 |
| --- | --- |
| 1 | 梳理高企申报书需要的企业主数据字段 |
| 2 | 对照企业资料模块，补齐缺失字段和专表 |
| 3 | 在企业资料中增加高企所需字段提示 |

| 5 | 创建申报和导出前生成资料快照 |

验收：

| 验收项 | 标准 |
| --- | --- |
| 资料有归口 | 公司信息只在企业资料中维护 |
| 申报可查看 | 企业申报能查看引用来源和当前值 |
| 缺失可处理 | 缺失字段能定位到具体企业资料页面 |

## 8. 不建议直接做的事项

| 事项 | 原因 |
| --- | --- |
| 直接运行 Flask 版 `declare-assistant` | 技术栈、账号体系、数据库、权限体系都和当前系统不一致 |
| 直接搬 SQLite 表结构 | 当前系统已使用 MySQL + TypeORM，应保持统一 |
| 直接迁移 PDF 导出 | 原实现写死 macOS Chrome 路径，Windows/服务器不可用 |
| 第一版做全自动评分 | 企业资料字段不一定完整，人工确认更稳 |
| 第一版做 OCR 识别 IP 证书 | 原项目该能力已停用，投入产出不高 |
| 第一版接 LLM 作为核心依赖 | AI 可增强体验，但不能作为主流程硬依赖 |
| 在申报书页面维护企业基本信息 | 会形成两套主数据入口，后续容易数据不一致 |

## 10. 最小可交付版本

最小版本只做下面 5 件事就有业务价值：

1. 高企项目详情页出现“评分测算”。
2. 企业能录入或确认四大模块评分输入。
3. 系统输出总分、达标线、分项得分和风险等级。
4. 系统给出缺口建议，并关联材料准备度。
5. 创建高企申报草稿后，评分结果进入我的申报详情。

这版上线后，企业和项目老师已经可以围绕“是否值得申报、优先补什么材料”协同工作。申报书填报、Word 导出和 AI 撰写可以作为后续增强。
