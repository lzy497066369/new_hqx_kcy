# AI 能力嵌入现有页面开发规划

## 1. 目标

本规划用于指导 AI 大模型能力接入当前系统。

当前策略不是单独建设一批 AI 页面，而是把 AI 能力嵌入现有业务页面，让用户在政策、企业、申报、审核等原有流程里直接使用 AI。

推荐方向：

```text
统一 AI 后端能力
  -> 通用 AI 前端组件
    -> 嵌入现有政策、企业、申报、审核页面
      -> AI 结果人工确认后再回写业务
```

## 2. 总体原则

- 不优先新增独立 AI 菜单和大量 AI 页面。
- AI 能力优先出现在现有业务页面里。
- 前端用通用 AI 按钮、抽屉、建议面板复用。
- 后端统一封装 AI 调用、任务记录、结果记录和审计日志。
- AI 只做建议、诊断、摘要、草稿、匹配和风险提示。
- 审核、通过、退回、正式提交等关键动作必须由人工确认。
- AI 输出不直接覆盖业务主表，先进入 AI 结果记录，确认后再回写。

## 5. 第一阶段优先改造点

第一阶段建议只做主链路上的 5 个点，避免范围过大。

### 5.1 后台政策文件页：AI 解析政策

入口：

```text
政策文件列表或详情 -> AI解析
```

输出：

- 政策名称
- 适用区域
- 申报对象
- 申报条件
- 材料清单
- 申报时间
- 奖励或补贴标准
- 主管部门
- 风险点和特殊限制

结果处理：

```text
AI 解析结果 -> 抽屉展示 -> 人工确认 -> 写入政策项目或材料配置
```

### 5.2 后台政策项目页：AI 生成条件和材料

入口：

```text
政策项目表单 -> AI生成条件/材料
```

输出：

- 申报条件
- 材料清单
- 适用企业标签
- 可匹配字段建议
- 项目风险提示

结果处理：

```text
AI 结果填入表单草稿 -> 人工编辑 -> 保存正式项目
```

### 5.3 后台企业档案详情：AI 企业体检

入口：

```text
企业档案详情 -> AI企业体检
```

输出：

- 企业资料缺口
- 高风险字段
- 适合申报项目
- 不满足条件
- 建议补齐动作
- 推荐跟进优先级

结果处理：

```text
AI 诊断结果 -> 展示建议 -> 可生成跟进任务或补件提醒
```

### 5.4 客户端企业资料首页：AI 资料体检

入口：

```text
企业资料首页 -> AI资料体检
```

输出：

- 当前资料完整度摘要
- 缺失模块
- 建议优先补齐项
- 可申报方向提示
- 需要上传的附件建议

结果处理：

```text
AI 建议 -> 用户点击跳转对应资料模块补齐
```

### 5.5 客户端项目或申报详情：AI 材料诊断

入口：

```text
项目详情/申报详情 -> AI材料诊断
```

输出：

- 材料是否齐全
- 缺失材料
- 问题字段
- 附件风险
- 补齐建议
- 申报风险提示

结果处理：

```text
AI 诊断 -> 用户补资料 -> 后台审核时可查看诊断记录
```

## 7. 后端 AI 服务规划

前端可以嵌入现有页面，但后端必须统一封装 AI 能力。

建议新增：

```text
backend/src/ai
```

核心模块：

| 模块 | 作用 |
| --- | --- |
| `AiController` | 统一 AI 接口入口 |
| `AiService` | 按 `scene` 分发不同业务场景 |
| `AiGatewayService` | 统一调用大模型 |
| `AiPromptService` | 管理或组装提示词 |
| `AiTask` | AI 任务记录 |
| `AiResult` | AI 结构化结果 |
| `AiAuditLog` | 模型、提示词、响应、token、成本、操作者审计 |

统一接口建议：

```text
POST /ai/tasks
GET /ai/tasks/:id
POST /ai/tasks/:id/confirm
POST /ai/tasks/:id/reject
```

创建任务参数示例：

```json
{
  "scene": "policy_parse",
  "bizType": "policy_file",
  "bizId": 123
}
```

## 10. 开发顺序

建议按下面顺序推进：

1. 后端新增统一 AI 服务基础结构。
2. 后端新增 `POST /ai/tasks` 和 `GET /ai/tasks/:id`。
3. 后端支持第一个场景 `policy_parse`。
4. 后台政策文件页接入 `AI解析` 按钮和结果抽屉。
5. 后台政策项目页支持应用政策解析结果。
6. 后端支持 `enterprise_check`。
7. 后台企业档案详情接入 `AI企业体检`。
8. 客户端企业资料首页接入 `AI资料体检`。
9. 后端支持 `material_check`。
10. 客户端项目或申报详情接入 `AI材料诊断`。
11. 再扩展 `review_assist` 和 `gaoxin_score_explain`。

## 11. 第一版 MVP 闭环

第一版建议形成这个闭环：

```text
后台录入或上传政策
  -> 点击 AI 解析政策
  -> AI 输出项目条件、材料清单、申报时间、奖励标准
  -> 后台人工确认
  -> 生成或补全政策项目
  -> 企业档案点击 AI 企业体检
  -> 输出推荐项目和缺失材料
  -> 客户端企业资料页展示补齐建议
  -> 企业补资料
  -> 项目或申报详情做 AI 材料诊断
```

## 12. 不建议第一阶段做的内容

- 不做独立 AI 聊天机器人作为主入口。
- 不做大量独立 AI 页面。
- 不做 AI 自动审批。
- 不做 AI 自动提交政府系统。
- 不做无审计记录的 AI 自动改业务数据。
- 不做复杂 Prompt 模板后台管理，第一版可以先代码内置。
- 不做向量知识库作为前置依赖，等政策库结构化稳定后再考虑。

## 13. AI 请求记录与统计规范

AI 模块必须记录每次真实请求和真实返回数据，用于后续审计、排查、统计、成本核算和效果复盘。

注意边界：

```text
真实请求和返回数据：保存到数据库
Markdown 文档：只写记录规范、字段说明、接口说明、统计口径和示例
```

### 13.1 记录原则

- 每次 AI 调用都必须生成 `ai_tasks` 记录。
- 每次 AI 调用都必须生成 `ai_audit_logs` 记录。
- AI 成功时必须生成 `ai_results` 记录。
- AI 失败时也必须记录请求、错误、耗时和失败状态。
- `prompt` 必须保存真实发送给模型的完整内容。
- `raw_response` 必须保存模型返回的完整原始内容。
- `input_snapshot` 必须保存当次调用读取到的业务数据快照。
- 不对数据库中的真实请求和真实返回做脱敏。
- 前端和业务页面展示时，可以按权限决定是否隐藏敏感字段，但底层审计数据保持完整。
- 不把真实请求和真实返回逐条写入 Markdown 文档。

### 13.2 每次请求必须记录的字段

| 类型 | 字段 | 说明 |
| --- | --- | --- |
| 任务 | `task_id` | 对应 AI 任务 ID |
| 场景 | `scene` | AI 场景，如 `policy_parse`、`enterprise_check` |
| 业务对象 | `biz_type` | 业务类型，如 `policy_file`、`enterprise_profile` |
| 业务对象 | `biz_id` | 业务数据 ID |
| 用户 | `created_by` | 触发 AI 调用的用户 |
| 服务商 | `provider` | OpenAI-compatible provider，当前默认接入小米 MiMo |
| 模型 | `model` | 如 `mimo-v2.5-pro` |
| 输入快照 | `input_snapshot` | 当次调用读取的业务数据快照，保存真实内容 |
| 请求内容 | `prompt` | 实际发送给模型的完整提示词，保存真实内容 |
| 原始返回 | `raw_response` | 小米 MiMo 返回的完整原始响应，保存真实内容 |
| 结构化结果 | `structured_result` | 系统解析后的 JSON 结果 |
| token | `prompt_tokens` | 输入 token 数 |
| token | `completion_tokens` | 输出 token 数 |
| token | `total_tokens` | 总 token 数 |
| 耗时 | `duration_ms` | 请求耗时 |
| 成本 | `cost` | 预估或实际费用 |
| 状态 | `status` | `pending`、`running`、`success`、`failed` |
| 错误 | `error_message` | 失败原因 |
| 时间 | `created_at` | 创建时间 |
| 时间 | `finished_at` | 完成时间 |

### 13.3 表结构职责

| 表 | 职责 |
| --- | --- |
| `ai_tasks` | 记录一次业务侧 AI 任务，包括场景、业务对象、状态、输入快照、创建人和完成时间 |
| `ai_results` | 记录 AI 结构化结果，包括摘要、结构化 JSON、置信度、确认状态和确认人 |
| `ai_audit_logs` | 记录模型调用审计，包括服务商、模型、完整 prompt、完整 raw response、token、耗时、成本和错误 |

### 13.5 统计口径

| 指标 | 口径 |
| --- | --- |
| 请求次数 | `ai_tasks` 创建数量 |
| 成功次数 | `ai_tasks.status = success` |
| 失败次数 | `ai_tasks.status = failed` |
| 成功率 | 成功次数 / 请求次数 |
| 输入 token | `ai_audit_logs.prompt_tokens` 汇总 |
| 输出 token | `ai_audit_logs.completion_tokens` 汇总 |
| 总 token | `ai_audit_logs.total_tokens` 汇总 |
| 平均耗时 | `ai_audit_logs.duration_ms` 平均值 |
| 费用 | `ai_audit_logs.cost` 汇总 |
| 场景统计 | 按 `scene` 分组 |
| 模型统计 | 按 `provider + model` 分组 |
| 用户统计 | 按 `created_by` 分组 |

```text
消耗了多少 token
是否成功
失败原因是什么
```

### 13.8 权限与安全边界

- 数据库保存完整真实记录。
- 后台查看完整请求和返回内容需要权限控制。
- 普通业务用户不应直接看到完整 `prompt` 和 `raw_response`。
- 生产环境日志文件不应额外打印完整 API Key。
- `AI_API_KEY` 只能保存在 `.env` 或密钥管理服务中，不能写入 Markdown、前端代码或提交记录。
- 删除或导出 AI 审计记录需要单独权限。

## 14. 验收标准

第一阶段验收可以按下面判断：

- 现有页面能看到 AI 操作入口。
- AI 调用有任务记录。
- AI 成功或失败状态可见。
- AI 结果可以结构化展示。
- AI 结果需要人工确认后才能应用。
- AI 输出能落到政策解析、企业体检或材料诊断中的至少一个真实业务场景。
- AI 调用有基础审计日志，能追溯输入、输出、模型和操作者。
- AI 调用能在数据库中看到完整真实请求和完整真实返回。

## 15. 结论

当前最合适的开发方式是：

```text
不单独堆 AI 页面
先做统一 AI 服务
再做通用 AI 前端组件
最后把 AI 嵌入现有政策、企业、申报、审核页面
```

第一批建议优先接：

```text
政策文件 -> 政策项目 -> 企业档案 -> 企业资料首页 -> 项目/申报详情
```

这样既能保持现有系统结构稳定，也能最快做出 AI 的业务效果。
