# 政策采集任务与待审查开发规划

## 1. 目标

建设“政策采集任务中心”，让后台管理员可以按“统一政策项目 + 区域 + 关键词/主管部门 + 执行周期”创建采集任务。

系统按任务执行政策搜索与分析，保存每次执行结果；当发现新增政策、疑似变更政策或不确定政策时，进入“政策待审查”页面。人工审查通过后，再写入正式的区域政策文件 `biz_region_policy_file`。

核心原则：

- 不直接自动写入正式政策文件。
- 每个采集任务必须有执行记录。
- 每次执行必须有返回结果和统计。
- 每条发现结果必须可追溯到来源、AI 记录和审查结果。
- 发现新增或变更时，必须在我的工作台展示提醒。
- AI 负责搜索、判断、解析、比对和建议；人负责最终确认。

## 2. 业务流程

```text
创建政策采集任务
  -> 选择统一政策项目
  -> 选择采集区域
  -> 配置关键词、主管部门、执行周期
  -> 手动执行 / 定时执行
  -> AI 搜索官方政策
  -> 官方性校验
  -> AI 解析政策内容
  -> 和现有区域政策文件比对
  -> 保存执行记录和结果明细
  -> 新增/变更/不确定结果进入待审查
  -> 我的工作台展示待审核提醒
  -> 人工审查
  -> 生成正式区域政策文件 / 更新原政策 / 忽略
```

## 4. AI 能力边界

统一走后端 AI 模块，不在政策模块里直接散写 AI 调用。

新增 AI 场景建议：

```text
policy_collect_search       // 根据项目、区域、关键词搜索候选官方政策
policy_official_verify      // 判断是否官方正式文件
policy_content_parse        // 解析政策正文结构化内容
policy_compare              // 与现有政策比对，判断新增/变更/一致
```

每次 AI 调用仍写入：

```text
ai_tasks
ai_results
ai_audit_logs
```

注意：

- “抓取”在业务上表示自动寻找政策，但实现上建议抽象为 `PolicySearchProvider`。
- 第一版当前接入小米 MiMo OpenAI-compatible API，并通过 web_search tool 启用联网搜索；如果模型搜索能力不稳定，后续可以替换为官方站内搜索接口、搜索 API 或人工指定来源。
- 不管搜索来源是什么，入正式库前必须进入待审查。

## 6. 比对规则

比对对象：`policy_collect_run_items` vs `biz_region_policy_file`。

优先级：

```text
1. document_no 文号
2. official_url 官方链接
3. title 标题
4. issuing_agency 发布机关
5. publish_date 发布日期
6. content_hash 正文 hash
7. attachment_hash 附件 hash
```

判断结果：

```text
new
  找不到匹配政策，进入待审查。

changed
  文号/标题/官方链接匹配，但正文 hash 或附件 hash 不一致，进入待审查。

same
  已存在且内容一致，只记录执行结果，不进入待审查。

uncertain
  AI 或规则无法确定是否同一政策，进入待审查。

ignored
  非官方、明显无关或人工忽略。
```

## 13. 风险和约束

### 13.1 AI 搜索能力不稳定

如果小米 MiMo `web_search` 不能稳定联网搜索，需要保持可替换的 `PolicySearchProvider`。

可选实现：

```text
小米 MiMo web_search 联网搜索能力
搜索 API
官方站内搜索接口
人工指定官方来源
```

### 13.2 官方性判断不能完全交给 AI

必须结合规则：

```text
官方域名白名单
发布机关
发布日期
文号
官方链接
附件来源
```

### 13.3 正式入库必须人工确认

不允许 AI 搜到结果后直接写入 `biz_region_policy_file`。

### 13.4 工作台提醒必须纳入 P0

否则采集结果容易沉没，业务闭环不完整。

## 16. `policy_collect_search` 请求与返回记录

### 16.1 调用入口

政策采集任务手动执行或定时执行时，会调用统一 AI 模块：

```text
PolicyCollectService.generateCandidates()
  -> AiService.runPolicyCollectSearch()
  -> AiGatewayService.chat()
  -> OpenAiCompatibleProvider.chat()
  -> POST https://api.xiaomimimo.com/v1/chat/completions
```

AI 场景：

```text
scene: policy_collect_search
bizType: policy_collect_run
bizId: policy_collect_runs.id
```

每次调用会落库：

```text
ai_tasks.input_snapshot      // 业务入参、messages、responseFormat
ai_results.structured_result // AI 返回 JSON 结构化结果
ai_audit_logs.prompt         // 实际 prompt
ai_audit_logs.raw_response   // 小米 MiMo 真实返回
ai_audit_logs.token_usage    // token 使用情况
```

### 16.2 业务请求参数

`AiService.runPolicyCollectSearch()` 的入参：

```json
{
  "bizId": "执行记录ID，例如 policy_collect_runs.id",
  "jobId": "采集任务ID",
  "jobName": "采集任务名称",
  "projectName": "统一政策项目名称",
  "regionName": "采集区域名称",
  "keywords": ["搜索关键词1", "搜索关键词2"],
  "departmentName": "主管部门，可为空",
  "officialDomainRules": "官方来源规则，可为空"
}
```

字段说明：

```text
bizId
  当前采集执行记录 ID，用于 AI 任务和政策采集 run 关联。

jobId / jobName
  采集任务信息，用于 prompt 和追溯。

projectName
  统一政策项目，例如“高新技术企业”。

regionName
  采集区域，例如“浙江省”“杭州市”。

keywords
  系统由 projectName、regionName 和人工关键词合并去重。

departmentName
  主管部门，例如“科技局”。为空时 prompt 使用“未指定”。

officialDomainRules
  官方来源规则。为空时使用默认规则：
  优先政府官网、主管部门官网、官方公告平台、官方政务服务平台；
  不要采用公众号、自媒体、转载站、新闻二次报道作为正式来源。
```

### 16.3 AI messages 结构

系统消息：

```json
{
  "role": "system",
  "content": "你是政策文件采集解析助手。优先返回官方正式政策文件，也可以返回高度相关但日期或官方性需要人工核验的候选；不要返回明显无关的解读稿、新闻稿、转载页或非官方页面。必须输出 JSON，不要输出 Markdown。"
}
```

用户消息模板：

```text
采集任务：{jobName}
统一政策项目：{projectName}
区域：{regionName}
主管部门：{departmentName 或 未指定}
```

## 17. 政策采集搜索链路调整

### 17.1 调整原因

原实现只有一次 `policy_collect_search` AI 请求：

```text
采集任务 -> 让模型自行联网搜索并直接返回政策 items
```

实际返回过 `{"items":[]}`，说明 compatible-mode 下模型可能没有真正拿到可用搜索结果，或者搜索过程不可审计。

新实现拆成两次 AI 请求：

```text
政策采集任务
-> PolicySearchProvider 生成官方搜索词
-> AI 官方搜索 policy_collect_official_search
-> 后端过滤官方 URL
-> AI 候选解析 policy_collect_search
-> 写入政策采集结果 / 待审查
```

这不是后端爬虫，不抓取网页 HTML；搜索动作仍走 AI 模块和小米 MiMo `web_search` 能力。后端只负责生成搜索词、过滤官方域名、记录搜索结果，并把可审计的候选来源交给 AI 解析。

### 17.2 AI 官方搜索请求

场景：

```text

bizType = policy_collect_run
bizId = policy_collect_runs.id
```

请求输入字段：

```json

  "bizId": "采集执行ID",

  ]
}
```


### 17.3 AI 候选解析请求

场景：

```text
scene = policy_collect_search
bizType = policy_collect_run
bizId = policy_collect_runs.id
```

请求输入字段新增：

```json
{
  "searchTaskId": "官方搜索AI任务ID",
  "searchResults": [
    {
      "query": "命中的搜索词",
      "title": "网页标题",
      "url": "官方URL",
      "snippet": "搜索摘要或页面关键内容",
      "source": "来源站点或部门",
      "publishDate": "YYYY-MM-DD或空",
      "officialLikely": true,
      "officialReason": "为什么像官方正式来源"
    }
  ]
}
```

解析要求：

```text
1. 只能基于 searchResults 解析政策文件。
2. 不得编造 searchResults 之外的 URL。
3. 排除新闻解读、转载、聚合、自媒体。
4. 明显不是政策文件、明显非官方/不可信来源时不生成 items；日期或官方性待核验但高度相关的候选可以生成 items 进入待审查。
5. searchResults 为空时应返回 {"items":[]}。
```

当传入 `searchResults` 时，解析请求不再传 `enable_search`，避免第二次 AI 自行扩展搜索范围。

### 17.4 采集执行记录字段

`policy_collect_runs.searched_keywords` 现在保存 JSON 对象：

```json
{
  "keywords": ["高新技术企业", "浙江省"],
  "queries": [
    "site:gov.cn 高新技术企业 浙江省 政策 文件 通知"
  ],
  "searchTaskId": "12",
  "rawResultCount": 8,
  "resultCount": 3,
  "warnings": []
}
```

统计口径：

```text
rawResultCount
  AI 官方搜索原始返回条数。

resultCount
  后端官方域名过滤后进入解析阶段的条数。

totalCount
  AI 候选解析后实际写入 policy_collect_run_items 的条数。

newCount / changedCount / sameCount / uncertainCount / ignoredCount
  仍按 policy_collect_run_items 的 compareStatus / status 统计。
```

### 17.5 空结果排查顺序

```text
1. 在 AI 记录页面按 bizId = 采集执行ID 查询。
2. 先看 policy_collect_official_search：
   - prompt 中 queries 是否正确。
   - raw_response 是否有 results。
   - results URL 是否为 gov.cn / *.gov.cn。
3. 再看 policy_collect_search：
   - input.searchResults 是否为空。
   - raw_response 是否返回 items。
4. 如果官方搜索有结果但 resultCount = 0，说明后端官方域名过滤未通过。
5. 如果 resultCount > 0 但 totalCount = 0，说明 AI 认为候选来源不是正式政策文件。
```

### 17.6 手动执行接口异步化

`POST /api/policy/collect-jobs/{id}/run` 只负责创建一条执行记录并立即返回：

```json
{
  "id": "采集执行ID",
  "jobId": "采集任务ID",
  "status": "running",
  "startedAt": "开始时间",
  "totalCount": 0
}
```

后端后台继续执行：

```text
1. 官方搜索 policy_collect_official_search
2. 候选解析 policy_collect_search
3. 比对正式政策文件
4. 写入 policy_collect_run_items
5. 更新 policy_collect_runs.status / finished_at / 统计数量
6. 生成工作台通知
```

前端手动执行后直接跳转采集结果页，按执行记录查看进度。接口不再同步等待 AI 搜索和解析完成，避免请求耗时过长或前端超时。

删除采集任务：

```text

```

删除规则：

```text

2. 历史执行记录、AI 记录、采集结果和通知保留，便于追溯。
```

### 18.5 采集时间范围

政策采集只取“当前日期往前一年”的数据，不按上一自然年计算。

示例：

```text
当前日期：2026-07-06
采集范围：2025-07-06 至 2026-07-06
```

后端会在三处控制：

```text
1. 搜索词带入起止年份，避免完整日期过窄导致召回不足。
2. AI 官方搜索 prompt 显式传入系统当前日期和采集日期范围，优先要求发布日期/公示日期/申报通知日期落在范围内。
3. AI 解析后只过滤明确早于或晚于范围的候选；没有日期、日期无法解析但来源/标题/摘要高度相关的候选先进入待审查，并在 AI 理由中标记“日期待核验”。
```

当前放宽策略：

```text
为提高召回率，搜索和候选生成阶段不再因为缺少发布日期直接丢弃结果。
正式写入区域政策文件前仍必须人工审查，日期不明确的候选需要审核人员确认后再导入或忽略。
AI 不得使用模型知识库中的旧当前年份判断日期范围；例如系统当前日期为 2026-07-06 时，2025-07-06 至 2026-07-06 是有效历史范围，不是未来时间。
```
