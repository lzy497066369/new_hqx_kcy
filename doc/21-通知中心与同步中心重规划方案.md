# 通知中心与同步中心重规划方案

## 1. 目标

这次重规划同时覆盖：

- 客户端 `vue-admin/apps/web-client`
- 后台管理系统 `vue-admin/apps/web-admin`
- 右上角通知入口
- 右上角同步入口
- 工作台提醒、列表页、状态流转、接口和数据模型

核心目标不是“再加两个图标”，而是把下面两件事彻底分清：

- 通知：告诉用户“发生了什么、需不需要你处理”
- 同步：告诉用户“系统正在跑什么、跑到哪了、有没有失败”

## 2. 当前现状判断

### 2.1 通知现状

- 客户端和后台右上角通知都还是模板态，实际数据写死在布局文件里。
- 后台工作台只有“政策采集通知”这一条业务线真正接上了。
- 客户端工作台的通知区仍是预留文案，没有真实通知流。
- 后端 `dashboard` 返回的 `notificationSummary` 仍是占位描述。

对应现状文件：

- `vue-admin/apps/web-admin/src/layouts/basic.vue`
- `vue-admin/apps/web-client/src/layouts/basic.vue`
- `vue-admin/apps/web-admin/src/views/dashboard/workspace/index.vue`
- `vue-admin/apps/web-client/src/views/dashboard/workspace/index.vue`
- `backend/src/modules/dashboard/dashboard.service.ts`

### 2.2 同步现状

- 客户端“同步”更多是页面级刷新、企业切换后刷新上下文、基础资料远端回填，没有统一入口。
- 后台“同步”更多是政策采集执行、企业导入同步、AI 分析、批量处理，但这些状态散在具体页面里。
- 用户现在很难判断：
  - 哪些任务在后台跑
  - 是否已经完成
  - 失败后去哪里看
  - 哪些结果会再变成通知

对应现状文件：

- `vue-admin/apps/web-client/src/store/client-enterprise.ts`
- `vue-admin/apps/web-client/src/views/client/home/index.vue`
- `vue-admin/apps/web-client/src/views/client/enterprise-profile/basic/use-enterprise-basic-profile.ts`
- `vue-admin/apps/web-admin/src/api/policy/collect.ts`
- `vue-admin/apps/web-admin/src/views/policy/collect/run-list.vue`

## 3. 重规划总原则

### 3.1 一句话定义

- 通知中心：面向人，解决“要不要看、要不要处理”
- 同步中心：面向过程，解决“系统有没有在跑、跑得怎么样”

### 3.2 统一交互原则

- 右上角保留两个相邻入口：`通知` + `同步`
- 两个入口打开同一套“协同中心”抽屉，只是默认 tab 不同
- 工作台展示摘要卡片，右上角展示即时状态
- 重要事项先进通知，长过程先进同步，过程结束后再产出通知

### 3.3 角色视角分离

- 客户端强调“和当前企业有关”的提醒与进度
- 后台强调“我负责处理的企业/任务”的提醒与进度
- 管理员看到全局或责任范围
- 企业用户只看到当前企业上下文和本人相关动作

## 4. 右上角入口重规划

## 4.1 入口结构

右上角建议固定为：

- 铃铛：通知中心
- 双箭头/旋转图标：同步中心

展示规则：

- 通知中心显示未读数红点
- 同步中心显示运行中数量，失败时优先红点
- 没有运行任务时不同步隐藏入口，只弱化显示

## 4.2 打开方式

点击后统一打开右侧抽屉，标题建议叫：

`协同中心`

抽屉内固定两个 tab：

- 通知
- 同步

好处：

- 用户只记一个右侧面板
- 不把“消息”和“进度”混成一锅
- 后续移动端也容易降级成一个页面

## 4.3 抽屉首屏内容

通知 tab 首屏：

- 未读摘要
- 今日重要提醒
- 最近 10 条通知
- 标记已读 / 全部已读 / 查看全部

同步 tab 首屏：

- 运行中
- 等待中
- 失败
- 最近完成
- 重试失败任务
- 查看详情日志

## 5. 通知中心规划

## 5.1 客户端通知分类

客户端只保留和企业用户动作直接相关的通知：

- 申报通知
  - 新建申报成功
  - 材料缺失
  - 审核退回
  - 即将截止
- 资料通知
  - 企业资料待补全
  - 材料校验失败
  - 基础资料更新成功
- 政策通知
  - 命中新的可申报政策
  - 关注政策即将截止
  - 政策状态更新
- 账号通知
  - 企业切换成功
  - 绑定企业待确认
  - 账号信息变更
- 系统通知
  - 平台公告
  - 维护提醒

客户端不应该出现：

- 后台运维型系统告警
- 与当前企业无关的全局业务提醒
- 纯技术日志式消息

## 5.2 后台通知分类

后台通知按“待处理业务”组织：

- 审核通知
  - 企业资料待审核
  - 申报待审核
  - 材料退回后待复核
- 政策通知
  - 政策采集待审查
  - 疑似变更政策
  - 采集失败
- 企业通知
  - 新企业导入完成
  - 企业资料长期未完善
  - 关键企业异常
- AI/任务通知
  - AI 分析完成
  - AI 任务失败
  - 导出包生成完成
- 系统通知
  - 权限变更
  - 平台公告

## 5.3 通知级别

建议统一四级：

- `critical`：必须处理，红色
- `high`：重要待办，橙色
- `medium`：普通提醒，蓝色
- `low`：信息通知，灰色

## 5.4 通知卡片字段

每条通知建议统一字段：

- `id`
- `portalType`：`admin` / `client`
- `category`
- `level`
- `title`
- `content`
- `actionText`
- `actionPath`
- `sourceType`
- `sourceId`
- `targetUserId`
- `targetEnterpriseId`
- `status`：`unread` / `read` / `archived`
- `createdAt`
- `readAt`

## 5.5 通知交互规则

- 点开通知即标记已读，但支持“仅预览不已读”作为后续增强
- 有明确动作的通知必须带跳转
- 列表只保留近 30 天，历史可归档
- 同类重复通知要合并，不要刷屏

合并示例：

- “材料校验失败”同一天同企业同模块合并为 1 条
- “政策命中提醒”同一批次按项目聚合

## 6. 同步中心规划

## 6.1 同步中心定义

同步中心不等于“刷新按钮”，而是系统内所有异步或准异步任务的统一状态面板。

纳入同步中心的任务必须满足至少一个条件：

- 耗时超过 3 秒
- 用户离开页面后任务仍继续
- 有明确进度或阶段
- 可能失败并需要重试

## 6.2 客户端同步类型

客户端建议纳入：

- 企业上下文刷新
  - 切换公司后刷新当前企业
- 资料同步
  - 基础资料远端拉取
  - 联系人/员工/财务等模块重新加载
- 材料处理
  - 上传
  - 解析
  - 自动校验
- 申报任务
  - 创建草稿
  - 生成材料清单
  - 导出申报包

客户端不同步纳入：

- 普通页面查询列表
- 本地表单输入
- 200ms 内即可完成的轻量请求

## 6.3 后台同步类型

后台建议纳入：

- 政策采集执行
- 政策待审查导入/更新
- 企业导入与资料同步
- AI 分析任务
- 导出任务
- 批量启停/批量处理

## 6.4 同步状态

统一状态建议：

- `queued`
- `running`
- `success`
- `failed`
- `partial_success`
- `cancelled`

辅助字段：

- `progress`
- `currentStep`
- `stepMessage`
- `retryable`
- `startedAt`
- `finishedAt`

## 6.5 同步与通知的关系

建议规则固定：

- 任务开始：进同步中心，不发通知
- 任务成功但无需用户处理：只留同步记录
- 任务成功且需要用户后续动作：产出通知
- 任务失败：同步标红，同时产出失败通知

示例：

- 客户端上传材料并自动校验
  - 上传中、解析中、校验中：同步中心显示
  - 校验通过：同步完成，不一定通知
  - 校验失败：同步失败 + 通知“材料校验失败，点击查看错误”

- 后台政策采集
  - 任务运行中：同步中心显示
  - 发现待审查结果：通知“新增 X 条待审查政策”
  - 任务失败：同步失败 + 通知“政策采集执行失败”

## 7. 工作台重规划

## 7.1 客户端工作台

客户端工作台不再写“通知入口暂留”，建议拆成两块：

- 通知摘要卡
  - 未读数
  - 最重要 3 条
  - 去消息中心
- 同步摘要卡
  - 运行中任务数
  - 最近失败任务
  - 最近完成任务
  - 去同步中心

客户端摘要优先展示：

- 审核退回
- 材料失败
- 截止临近
- 新匹配政策
- 导出/校验任务状态

## 7.2 后台工作台

后台工作台建议从单一“政策采集提醒”扩展为：

- 待审核通知摘要
- 同步任务摘要
- 政策采集摘要
- 企业资料异常摘要

其中“政策采集提醒”继续保留，但降级为通知中心的一条业务子集，不再独占整个通知概念。

## 8.2 第二阶段迁移建议

- `policy_collect_notifications` 逐步迁移为业务源表
- 通过 service 写入 `system_notifications`
- 后续其他业务线统一写 `system_notifications`

这样不会卡住现有政策采集功能，也能尽快把客户端和后台接到一个统一通知中心上。

## 9. 接口规划

## 9.1 通知接口

建议统一成当前用户语义：

```text
GET  /inbox/notifications/summary
GET  /inbox/notifications
POST /inbox/notifications/:id/read
POST /inbox/notifications/read-all
POST /inbox/notifications/:id/archive
```

返回摘要建议：

```json
{
  "unread": 6,
  "critical": 1,
  "high": 2,
  "latest": []
}
```

## 9.2 同步接口

```text
GET  /inbox/sync-jobs/summary
GET  /inbox/sync-jobs
GET  /inbox/sync-jobs/:id
POST /inbox/sync-jobs/:id/retry
```

返回摘要建议：

```json
{
  "queued": 1,
  "running": 2,
  "failed": 1,
  "latest": []
}
```

## 9.3 实时更新

建议优先级：

1. P0 先轮询
2. P1 再上 SSE

推荐：

```text
GET /inbox/stream
```

事件类型：

- `notification.created`
- `notification.read`
- `sync.updated`
- `sync.finished`

## 10. 前端实现建议

## 10.1 组件拆分

布局层不要再直接写 mock 数据，改成：

### 客户端

- `src/layouts/widgets/notification-center.vue`
- `src/layouts/widgets/sync-center.vue`
- `src/composables/use-inbox-notifications.ts`
- `src/composables/use-sync-jobs.ts`

### 后台

- `src/layouts/widgets/notification-center.vue`
- `src/layouts/widgets/sync-center.vue`
- `src/composables/use-inbox-notifications.ts`
- `src/composables/use-sync-jobs.ts`

如果后续两端交互完全一致，再往 `packages/effects/common-ui` 抽共享组件。

## 10.2 路由页建议

除了右上角抽屉，还应保留完整页：

- 客户端：`/client/inbox`
- 后台：`/system/inbox`

完整页结构：

- `通知`
- `同步`
- `全部`

这样便于做筛选、历史记录、失败重试和移动端承接。

## 10.3 Vue 实现边界

按现有项目结构，建议：

- 布局组件只负责放插槽和触发打开
- 数据加载逻辑放 composable
- 通知列表、同步列表拆成独立展示组件
- 工作台只消费 summary，不直接拼接口细节

## 11. 双端具体方案

- 铃铛：未读通知

## 11.2 后台最终形态

- 铃铛：待审核、任务失败、关键提醒

## 12. 落地顺序

## P0：统一右上角入口与真实数据接入

- 去掉两个布局里的 mock 通知
- 后台先接政策采集通知到右上角通知中心
- 客户端先接“资料/材料/申报”最小通知集
- 把“同步中心”先接政策采集任务和材料上传校验任务

验收：

- 右上角通知不再是写死数据
- 至少有 2 条真实业务链路可跑通

## P1：统一数据模型和工作台摘要

- 新增 `system_notifications`
- 新增 `system_sync_jobs`
- 客户端工作台接通知摘要和同步摘要
- 后台工作台从“单一政策采集提醒”升级为“通知 + 同步”

验收：

- 工作台和右上角读同一套 summary
- 失败任务能在同步中心看到并重试

## P2：实时化和历史化

- 接 SSE
- 增加完整列表页
- 增加归档、筛选、批量已读
- 增加同步详情日志

## 13. 这次重规划的关键结论

- 通知和同步不能再混着做
- 右上角应该是两个入口、一个抽屉、两套状态
- 工作台展示摘要，右上角展示即时提醒
- 后台先以政策采集为切入点，客户端先以材料校验和申报提醒为切入点
- 数据层先兼容旧表，再逐步统一到通用通知表和同步任务表
