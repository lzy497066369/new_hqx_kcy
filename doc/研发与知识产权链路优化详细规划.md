# 研发与知识产权链路优化详细规划

## 1. 文档说明

### 1.1 规划目标

统一规划研发与知识产权模块中的以下能力：

1. 成果转化草稿生成页面增加序号和数量提示。
2. RD、PS、成果转化关联 IP 时展示 `IP01`、`IP02`，不展示数据库 ID。
3. 基于《国家重点支持的高新技术领域》文档建立技术领域分类库，并由 AI 自动识别 IP、RD、PS、成果的技术领域。
4. 修复 PS 草稿无法入库的问题，并让失败原因可见、可处理。
5. 建立完整的 `IP -> RD -> PS -> 成果转化 -> 合同/发票` 证据链，并统一展示各类业务编号。

### 1.2 适用范围

- 客户端“研发与知识产权”页面。
- IP 识别与入库。
- RD 手工生成、AI 生成和自动匹配。
- 成果转化草稿生成、编辑、删除、审核入库。
- PS 草稿生成、编辑、删除、审核入库。
- 证据链、申报材料和企业资料详情中的关联展示。

### 1.3 非目标

- 不改变现有企业数据的归属关系。
- 不把展示编号写入关联字段。
- 不使用数据库自增 ID 作为业务编号。
- 不允许 AI 自由生成分类库之外的技术领域。
- 不因显示编号变化而重建已有 RD、PS、成果关联关系。

## 3. 总体设计

### 3.1 业务链路

```text
IP PDF 识别
    |
    v
IP 正式记录 + IP 编号 + 技术领域
    |
    +----> 成果转化草稿
    |          |
    |          v
    |      成果转化正式记录 + 成果编号
    |
    +----> RD 自动匹配/手工生成
                  |
                  v
              RD 正式记录 + RD 编号
                  |
                  +----> PS 草稿
                              |
                              v
                          PS 正式记录 + PS 编号
                              |
                              v
合同/发票/验收材料形成证据闭环
```

### 3.2 编号和关联的基本原则

1. 数据库存储使用真实 ID。
2. 页面、导出、证据链使用业务编号。
3. 所有编号均在企业范围内生成。
4. 编号变更不能改变关联字段。
5. 任何关联 ID 都必须校验 `enterprise_id` 和 `record_type`。
6. 页面展示必须避免出现裸数据库 ID。

## 4. 编号规则

### 4.1 IP 编号

IP 编号排序规则：

1. 发明专利。
2. 实用新型。
3. 软件著作权。
4. 其他知识产权类型。
5. 同类型优先按申请日期升序。
6. 申请日期为空时使用授权/登记日期。
7. 日期仍相同时使用记录 ID 升序作为稳定排序。

展示示例：

```text
IP01  发明专利 A，申请日 2024-01-01
IP02  发明专利 B，申请日 2024-03-01
IP03  实用新型 A，申请日 2023-08-01
IP04  软件著作权 A，登记日 2024-02-01
```

### 4.2 RD 编号

RD 编号在当前企业范围内连续生成：

```text
RD01、RD02、RD03...
```

建议以正式入库顺序生成，删除后不立即重排历史 RD 编号，避免已经生成的申报材料失效。新生成 RD 使用当前最大编号加一。

### 4.3 PS 编号

PS 编号在当前企业范围内连续生成：

```text
PS01、PS02、PS03...
```

PS 草稿阶段可显示计划序号，正式入库后生成正式 PS 编号。删除后不修改已有 PS 编号。

### 4.4 成果转化编号

成果转化编号独立于 IP 编号，避免因为部分 IP 尚未形成成果导致编号跳号：

```text
成果01、成果02、成果03...
```

正式编号排序规则：

1. 按转化年度升序。
2. 转化年度相同时，按关联 IP 的授权/登记时间升序。
3. 仍相同时按关联 IP 的申请时间升序。
4. 仍相同时按成果正式记录 ID 升序。

成果编号变化不会改变 `related_ip_ids`、`related_rd_ids` 或 `related_ps_ids`。

### 4.5 草稿序号和正式编号的区别

成果转化草稿页面中的序号仅用于阅读：

```text
序号 1、2、3...
```

正式成果编号用于正式资料：

```text
成果01、成果02、成果03...
```

二者不能混用，也不把草稿序号写入数据库。

## 5. 成果转化草稿页面优化

### 5.1 页面调整

草稿表格增加第一列“序号”：

| 序号 | 状态 | 来源 IP | 成果名称 | 成果内容 | 技术描述 | 年度 | 方式 | 证明材料 | 审核提示 | 操作 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 待审核 | IP01 | xxx | xxx | xxx | 2024 | 自行实施 | xxx | 无 | 保存/删除 |

顶部增加统计：

```text
当前草稿：15 条
待审核：12 条
已拒绝：3 条
```

### 5.2 序号行为

- 草稿加载时按接口返回顺序编号。
- 删除一条草稿后重新计算展示序号。
- 筛选或分页时显示当前列表序号，必要时使用全局序号。
- 草稿序号不作为 Vue 的 `key`。
- Vue 的 `key` 继续使用草稿真实 ID。

### 5.3 来源 IP 展示

来源 IP 展示改为：

```text
IP01 - 一种卫星通信中加密传输方法
```

不得显示：

```text
330 - 一种卫星通信中加密传输方法
```

## 6. 关联编号展示方案

### 6.1 展示和存储分离

数据库：

```text
related_ip_ids = "312,313"
```

接口展示对象：

```json
{
  "id": "312",
  "code": "IP01",
  "label": "IP01 - 一种卫星通信中加密传输方法",
  "name": "一种卫星通信中加密传输方法"
}
```

表单选项的 `value` 使用 ID，`label` 使用业务编号和名称：

```json
{
  "value": "312",
  "label": "IP01 - 一种卫星通信中加密传输方法"
}
```

### 6.2 各类关联展示

| 关联类型 | 展示格式 |
| --- | --- |
| IP | `IP01 - 名称` |
| RD | `RD01 - 项目名称` |
| PS | `PS01 - 产品/服务名称` |
| 成果 | `成果01 - 成果名称` |

### 6.3 证据链展示

证据链页面建议采用节点方式：

```text
IP01 一种卫星通信中加密传输方法
  |
  +-- RD01 卫星通信智能组网关键技术研发项目
        |
        +-- PS01 卫星通信网络安全服务
              |
              +-- 成果01 卫星通信安全传输系统服务
                    |
                    +-- 合同 HT2026001
                    +-- 发票 FP2026001
```

每个节点需要显示：

- 业务编号。
- 名称。
- 数据库 ID 仅作为前端内部数据，不直接展示。
- 当前关联状态。
- 缺失材料提示。

## 7. 技术领域分类库和 AI 识别

### 7.1 文档处理原则

用户提供的《国家重点支持的高新技术领域.docx》是分类库原始来源，不建议在运行时直接读取电脑路径。

建议处理流程：

1. 离线解析 DOCX 文本。
2. 提取一级领域、二级领域、具体技术类目和排除项。
3. 清洗标题、编号、换行和重复内容。
4. 生成版本化分类数据。
5. 导入系统分类库。
6. 在系统中记录来源文件名、版本和导入时间。

生产环境不能依赖：

```text
E:/xwechat_files/...
```

### 7.2 建议分类表

建议新增技术领域分类表：

```text
biz_high_tech_field_catalog
```

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `version` | 分类库版本 |
| `code` | 分类编码 |
| `parent_code` | 父级分类编码 |
| `level` | 一级/二级/具体类目 |
| `name` | 分类名称 |
| `keywords_json` | 关键词和同义词 |
| `excluded_keywords_json` | 排除词 |
| `source_file` | 来源文件 |
| `status` | 是否启用 |

### 7.3 分类结果表

建议增加独立的 AI 分类结果表：

```text
biz_property_tech_classification
```

建议字段：

| 字段 | 说明 |
| --- | --- |
| `enterprise_id` | 企业范围 |
| `record_type` | IP/RD/PS/成果 |
| `record_id` | 业务记录 ID |
| `field_code` | 一级领域编码 |
| `sub_field_code` | 二级领域编码 |
| `category_code` | 具体类目编码 |
| `confidence` | AI 置信度 |
| `evidence_json` | 命中的名称、关键词和材料 |
| `source_snapshot` | 本次输入摘要 |
| `classifier_version` | 分类器版本 |
| `is_manual` | 是否人工确认 |
| `status` | 有效/历史 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

现有字段继续兼容：

- IP 的 `ip_tech_category` 保存展示用领域。
- RD 的 `project_type` 保存展示用领域。
- PS 的 `tech_field` 保存展示用领域。
- 成果可通过关联结果查询领域，或增加对应展示字段。

### 7.4 AI 输入来源

AI 分类输入按以下顺序组合：

1. IP 名称、专利名称、软著名称。
2. IP 技术描述、备注、摘要或识别文本。
3. RD 项目名称、核心技术、创新点和阶段成果。
4. PS 名称、关键技术、技术指标和竞争优势。
5. 成果名称、应用场景、技术描述。
6. 当前企业销售合同名称和合同描述。
7. 当前企业发票商品/服务内容。

### 7.5 推荐识别权重

推荐权重如下，后续通过真实数据校准：

| 来源 | 权重 |
| --- | ---: |
| IP/专利名称和技术文本 | 45% |
| RD、PS、成果技术文本 | 30% |
| 销售合同内容 | 15% |
| 发票内容 | 10% |

合同和发票作为业务应用场景补充，不能覆盖明显的 IP 技术事实。

### 7.6 AI 输出约束

AI 只能输出分类库中存在的编码：

```json
{
  "field_code": "ELECTRONIC_INFORMATION",
  "sub_field_code": "SOFTWARE",
  "category_code": "NETWORK_COMMUNICATION_SOFTWARE",
  "confidence": 0.91,
  "evidence": [
    "卫星通信",
    "智能组网",
    "数据传输"
  ],
  "needs_manual_review": false
}
```

当置信度不足时：

```text
待人工确认
```

不能自动把不确定结果写入正式申报字段。

### 7.7 识别时机

| 时机 | 行为 |
| --- | --- |
| IP 识别草稿生成 | 给出候选领域 |
| IP 审核入库 | 保存分类结果 |
| RD 自动匹配 | 使用 IP 领域进行分组 |
| PS 生成 | 结合 RD、成果、合同、发票重新判断 |
| 成果入库 | 继承关联 IP/RD 领域并允许人工调整 |

人工确认后的分类结果不允许被普通刷新覆盖。只有用户主动点击“重新识别”时才重新生成 AI 结果。

## 8. PS 入库问题修复方案

### 8.1 入库前校验

每条 PS 草稿入库前检查：

1. PS 名称不能为空。
2. PS 名称不能重复。
3. PS 名称不能使用“产品（服务）”等泛化名称。
4. 必须关联至少一个 RD。
5. RD 必须属于当前企业。
6. 建议至少关联一个 IP。
7. 关联 IP 必须属于当前企业。
8. 建议至少关联一个成果转化。
9. 关联成果必须属于当前企业。
10. 关系字段中的值必须是当前企业对应类型的真实 ID。
11. 合同和发票如填写，必须属于当前企业。

### 8.2 重点排查的现有问题

当前 PS 生成流程依赖“RD 已关联成果转化”作为可生成条件。需要重点检查：

- RD 的 `related_transformation_ids` 是否正确同步。
- 成果是否只关联了 IP，但没有反向同步到 RD。
- PS 草稿中的 `related_rd_ids` 是否为字符串数组、逗号字符串或空值。
- 前端展示编号后，是否错误地把 `IP01` 当作数据库 ID 提交。
- 草稿编辑后，`sourceIds` 是否与 `related_rd_ids` 同步。
- 审核接口是否逐条返回失败原因。

### 8.3 入库结果设计

批量审核不采用全部成功或全部失败：

```json
{
  "total": 3,
  "success": [
    { "draftId": "11", "recordId": "501" }
  ],
  "failed": [
    { "draftId": "12", "reason": "未关联 RD" },
    { "draftId": "13", "reason": "PS 名称已存在" }
  ]
}
```

前端处理：

- 成功草稿标记为已入库。
- 失败草稿继续保留。
- 失败原因显示在对应草稿行。
- 顶部显示成功数量和失败数量。
- 支持用户修正后重新审核。

### 8.4 企业数据范围校验

所有关联查询都必须同时限制：

```text
enterprise_id = 当前企业
record_type = 目标类型
status = 1
```

不能只根据 ID 查询，否则可能出现跨企业关联或误判。

## 9. 接口规划

`sequenceNo` 只用于页面展示，不参与审核和删除。

```json
{
```

### 9.3 技术领域接口

建议增加：

```text
GET  /client/enterprise/property/technology-fields
POST /client/enterprise/property/technology-fields/classify
POST /client/enterprise/property/technology-fields/confirm
POST /client/enterprise/property/technology-fields/reclassify
```

用途：

- 获取分类树。
- 预览 AI 识别结果。

- 用户主动重新识别。

### 9.4 PS 入库接口

现有审核接口保留，增强返回：

- 每条草稿失败原因。
- 失败字段。
- 关联数据缺口。
- 是否允许重新审核。

## 11. 后端实施拆分

### 阶段一：展示编号和序号

目标：先解决用户可见性问题。

- 成果草稿增加序号。
- 关联选项增加 `code` 和 `label`。
- 通用表格显示 IP/RD/PS/成果编号。
- 不改变数据库关联字段。

### 阶段二：PS 入库闭环

目标：确保 PS 能够明确入库或明确失败。

- 梳理 PS 草稿标准 payload。
- 修复关系 ID 转换。
- 增加企业范围校验。
- 优化审核失败返回。
- 前端展示逐条失败原因。
- 增加 PS 入库回归测试。

### 阶段三：证据链统一

目标：让 IP、RD、PS、成果和合同发票可以完整追踪。

- 后端统一构建证据链节点。
- 节点输出业务编号和名称。
- 补充双向关系同步。
- 生成缺口列表。
- 统一详情页展示。

### 阶段四：技术领域分类库

目标：将 DOCX 变成可维护的系统分类数据。

- 解析并清洗 DOCX。
- 建立分类库版本。
- 导入一级、二级和具体类目。
- 增加关键词和排除词。
- 增加分类结果表。
- 做一次历史 IP 数据初始化分类。

### 阶段五：AI 识别和自动回填

目标：结合 IP、RD、PS、合同、发票进行技术领域判断。

- 建立统一分类 Prompt。
- 增加结构化 JSON 校验。
- 增加置信度和证据记录。
- 增加人工确认。
- 接入 RD、PS、成果生成流程。
- 增加低置信度拦截。

## 12. 测试规划

### 12.1 后端单元测试

- IP 编号按类型和申请时间排序。
- 成果编号按转化时间连续生成。
- 关系 ID 转业务编号。
- 跨企业关系被拒绝。
- 不同记录类型的 ID 不能混用。
- PS 名称重复校验。
- PS 泛化名称校验。
- PS 缺少 RD 时返回明确原因。
- PS 缺少成果时返回明确原因。
- AI 分类结果只能使用分类库编码。
- 低置信度结果进入人工确认。

### 12.2 前端测试

- 成果草稿序号正确显示。
- 删除草稿后序号重新排列。
- 关联 IP 显示 `IP01` 而不是数据库 ID。
- RD、PS、成果关联显示业务编号。
- PS 批量入库显示成功/失败数量。
- PS 失败原因显示在对应草稿行。
- AI 领域结果可确认和手工修改。

### 12.3 集成测试

完整验证：

```text
IP 识别入库
  -> 生成成果并审核
  -> RD 自动匹配并审核
  -> 生成 PS 并审核
  -> 关联合同和发票
  -> 查看完整证据链
```

同时验证：

- 删除草稿不会影响正式记录。
- 删除正式记录会正确清理反向关系。
- 一个企业不能读取另一个企业的 IP、RD、PS 或成果。
- 业务编号变化不会改变内部关联。

## 13. 验收标准

### 13.1 成果草稿

- 页面能够清楚看到当前生成了多少条草稿。
- 每条草稿都有序号。
- 删除后序号无重复、无空洞。

### 13.2 关联显示

- 页面不再直接显示 IP、RD、PS、成果数据库 ID。
- 关联项统一展示业务编号和名称。
- 数据库关联字段仍保存真实 ID。

### 13.3 技术领域

- 分类结果来自《国家重点支持的高新技术领域》分类库。
- IP、RD、PS、成果均能查看分类结果。
- AI 能结合 IP、合同和发票内容判断。
- 低置信度结果不会直接作为最终分类。
- 用户可以人工确认和修改。

### 13.4 PS 入库

- 正常 PS 草稿可以审核入库。
- 失败 PS 草稿保留并显示原因。
- 失败原因可以指导用户修复。
- 批量入库不会因为一条失败导致全部结果丢失。

### 13.5 证据链

- IP、RD、PS、成果均显示业务编号。
- 可以从任一节点查看上下游关联。
- 缺少关联或材料时显示明确缺口。
- 合同、发票只显示当前企业数据。

## 14. 风险和处理建议

### 14.1 历史编号变化

IP 和成果重新编号可能影响已导出的申报材料。建议：

- 新规则只对页面和新生成数据生效，或提供一次性重排确认。
- 重排前保存编号变更记录。
- 已归档材料保留生成时的编号快照。

### 14.2 AI 分类误判

建议保留：

- AI 原始输入摘要。
- AI 输出结果。
- 命中证据。
- 分类库版本。
- 人工修改记录。

### 14.3 合同和发票数据不足

合同或发票内容不足时，AI 应降低置信度，不应编造销售场景。界面显示“依据不足，待人工确认”。

### 14.4 关联字段历史脏数据

上线前应执行只读检查：

- 是否存在跨企业 ID。
- 是否存在已删除记录 ID。
- 是否存在错误 record_type。
- 是否存在空关系、重复关系。

清洗历史数据前先生成备份和修复报告。

## 15. 推荐开发顺序

1. 成果草稿序号。
2. 关联编号展示。
3. PS 入库错误定位和修复。
4. IP-RD-PS-成果证据链展示。
5. DOCX 分类库导入。
6. AI 技术领域识别。
7. 合同、发票内容接入分类。
8. 全链路回归测试和历史数据核查。

该顺序优先解决页面可用性和 PS 入库问题，再接入技术领域 AI，减少一次性改动对现有链路的影响。
