# HQX 系统改进总体路线图

> 制定时间：2026-10-08
> 目标：系统化解决当前存在的架构、安全、代码质量、测试和运维问题
> 原则：不破坏现有功能，分阶段实施，每阶段可验证

## 一、改进优先级矩阵

| 优先级 | 影响范围 | 紧急程度 | 实施周期 | 风险等级 |
|--------|---------|---------|---------|---------|
| P0 | 安全/稳定性 | 立即 | 1-2 周 | 高 |
| P1 | 开发效率/质量 | 1 个月内 | 1-2 月 | 中 |
| P2 | 架构优化 | 3 个月内 | 3-6 月 | 中低 |
| P3 | 长期规划 | 6 个月+ | 6-12 月 | 低 |

## 二、分阶段实施计划

### 第一阶段：安全与稳定性加固（P0）— 2 周

**目标**：解决生产环境的安全隐患和稳定性问题

#### 1. 会话管理 Redis 迁移
- **当前问题**：单进程内存存储，无法水平扩展
- **方案文档**：`01-Redis会话迁移方案.md`
- **预期成果**：支持多实例部署，会话持久化
- **工作量**：3 天开发 + 2 天测试

#### 2. CRM v1 Token 废弃
- **当前问题**：静态 token 安全风险
- **方案文档**：`02-CRM集成安全加固方案.md`
- **预期成果**：所有 CRM 接入强制使用 v2 HMAC-SHA256
- **工作量**：2 天开发 + 1 天协调 CRM 端升级

#### 3. 企业数据隔离增强验证
- **当前问题**：依赖代码层面过滤，容易遗漏
- **方案文档**：`03-企业数据隔离增强方案.md`
- **预期成果**：自动化测试覆盖 + 代码扫描工具
- **工作量**：3 天实施

### 第二阶段：代码质量与测试（P1）— 2 个月

**目标**：提升代码可维护性，建立测试体系

#### 4. 巨型 Service 拆分
- **当前问题**：client.service.ts 853 KB，难以维护
- **方案文档**：`04-Service模块拆分方案.md`
- **预期成果**：按业务域拆分成 8-10 个独立 service
- **工作量**：1 周规划 + 2 周实施 + 1 周测试

#### 5. 测试体系建设
- **当前问题**：缺少单元测试和集成测试
- **方案文档**：`05-测试体系建设方案.md`
- **预期成果**：核心流程 80% 测试覆盖率
- **工作量**：持续 2 个月，与其他工作并行

#### 6. API 文档自动化
- **当前问题**：没有 Swagger UI，前端对接困难
- **方案文档**：`06-API文档自动化方案.md`
- **预期成果**：完整的 Swagger UI，自动生成
- **工作量**：3 天配置 + 5 天补充注解

#### 7. CI/CD 流程建立
- **当前问题**：手动构建和部署
- **方案文档**：`07-CICD流程建设方案.md`
- **预期成果**：自动化测试、构建、部署
- **工作量**：1 周设置 + 持续优化

### 第三阶段：架构优化（P2）— 3-6 个月

**目标**：解决架构层面的技术债

#### 8. 前端路由重构
- **当前问题**：大量 hideInMenu 路由，历史包袱重
- **方案文档**：`08-前端路由重构方案.md`
- **预期成果**：清晰的路由结构，统一命名规范
- **工作量**：2 周规划 + 3 周实施 + 1 周灰度

#### 9. IAM 统一认证
- **当前问题**：两套认证系统并存
- **方案文档**：`09-IAM统一认证迁移方案.md`
- **预期成果**：统一到 IAM 服务
- **工作量**：1 月规划 + 2 月开发 + 1 月灰度

#### 10. MySQL 升级规划
- **当前问题**：MySQL 5.6 版本过旧
- **方案文档**：`10-MySQL升级方案.md`
- **预期成果**：升级到 MySQL 8.0
- **工作量**：2 周准备 + 1 周升级 + 2 周验证

#### 11. Docker 容器化
- **当前问题**：缺少容器化支持
- **方案文档**：`11-Docker容器化方案.md`
- **预期成果**：完整的 Docker 镜像和编排
- **工作量**：1 周开发 + 1 周测试

### 第四阶段：长期优化（P3）— 6-12 个月

**目标**：提升系统的现代化程度和可维护性

#### 12. Monorepo 迁移
- **当前问题**：四个独立仓库，管理复杂
- **方案文档**：`12-Monorepo迁移方案.md`
- **预期成果**：统一代码仓库，简化版本管理
- **工作量**：2 周规划 + 2 周迁移 + 1 周适配

#### 13. 可观测性建设
- **当前问题**：日志、监控、追踪缺失
- **方案文档**：`13-可观测性建设方案.md`
- **预期成果**：完整的监控告警体系
- **工作量**：1 月集成 + 持续优化

#### 14. 微服务拆分评估
- **当前问题**：单体应用，耦合较重
- **方案文档**：`14-微服务拆分评估报告.md`
- **预期成果**：是否拆分的决策依据
- **工作量**：2 周评估 + 报告

## 六、实施原则

### 1. 零停机部署
- 所有改动必须支持灰度发布
- 保留回滚方案
- 监控关键指标

### 2. 向后兼容
- API 变更采用版本化（/api/v1、/api/v2）
- 旧接口保留至少 3 个月过渡期
- 提前通知前端和外部系统

### 3. 数据安全
- 所有涉及数据迁移的操作必须先备份
- 验证数据完整性
- 记录迁移日志

### 4. 文档先行
- 每个改进项先完成方案文档
- 方案评审通过后再实施
- 实施过程中同步更新文档

### 5. 小步快跑
- 每个改进项拆分成可独立验证的小任务
- 每完成一个任务立即合并和部署
- 快速反馈，及时调整
